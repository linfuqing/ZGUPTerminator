# 联机机器人 — 发布与测试分离

> **目的**：明确「共部署交付代码」与「Editor 自验证」的边界，避免为跑通 PlayMode 在发布热路径上掺入测试妥协。  
> **权威层级**：发布行为以 [联机机器人-架构约束.md](./联机机器人-架构约束.md)（M1–M7）为准；测试以本文 + [架构约束 §6.1](./联机机器人-架构约束.md#61-playmode-验收模拟真人操作交付门禁) 为准。

MultiplayerBot 的运行时、录制、Editor、测试和文档均归属本地 file package `cn.com.zerogame.unitypackages.terminator`（`ZGUPTerminator`），可以直接在包内维护。`BotConfig.asset` 仍是使用方工程配置，不随包发布。

## 1. 两个目标（不可混写）

| 维度 | **发布目标**（Release） | **测试目标**（Editor / PlayMode） |
|------|-------------------------|-----------------------------------|
| **部署形态** | `Server.unity` 与 Bot Farm **同进程共部署** | 加载 `Server.unity` + `World.Update`，模拟真人操作 |
| **热路径** | 单 Bot Listen Driver + `BotRelayFarmNative`；Connect/link 用 `EnqueueToListen`，业务用 `BotRelayInjectQueue`，下行用 `TryDequeueToBot` | 与发布相同 Server/Bot 热路径；**额外**可模拟第二个「真人 host」 |
| **Bot 连接** | Init 采原始 Connect 握手/hello/link UTP 模板；Connect 后业务经 Server inject API；**无** `ClientData` | Bot 仍走 Farm 注入；host 可用 Editor 专用手段 |
| **状态写入** | Bot **不写** `ReplyMessageShared`（M6） | Host 模拟可写 `ReplyMessageShared`（仅测试） |
| **约束文档** | [架构约束](./联机机器人-架构约束.md) 全文 | 不受 M6「禁止写 SharedStatic」约束于 **host 模拟**；仍须 PopEvents 无越界 |
| **程序集** | `Terminator.MultiplayerBot` | `Terminator.MultiplayerBot.Tests`（`includePlatforms: Editor`，TestAssemblies） |
| **允许妥协** | **仅诊断 LOG**（`[BotRelay]`、`diag*`） | HostTestClient、抓包 fixture 等 |

**一句话**：发布代码只服务「Server 里跑 N 个 Bot」；测试代码只服务「Editor 里证明这条链路与 Manual Play 一致」，且**不得**把测试专用双轨写进 WireCatalog / Farm 热路径。

## 3. 发布路径（必须保持）

与 [架构约束 §1–§3](./联机机器人-架构约束.md) 一致，摘要：

1. **单 Listen Driver**（M1）— 仅 `NetworkRelayServerSystem` 驱动 `ScheduleUpdate`。
2. **Bot → Server** — 仅原始 UTP Connect 握手/link 经 `BotRelayManager.EnqueueToListen(virtualPort, utpWire)`；Connect 后业务经 `BotRelayInjectQueue` → `NetworkRelayServerInjectSingleton` → Handler（M2/M4）。
3. **Server → Bot** — `RouteSend` → `TryDequeueToBot` → 当前 PopEvents framing → Inbox（M2）。原始 UTP Connect 握手不进入 app 分类；应用层 `NetworkRelayMessageType.Connect(type=0)` 是远端成员重连状态，必须按 `[Connect, channelFlag, userID] + EOF` 精确解析。
4. **WireCatalog** — Init 一次性采 **Bot 原始 UTP Connect 握手** / server hello / link ACK；另以 live Null-pipeline 当前 Invite Capture 只测量 `inboundAppPayloadOffset`，不保存 Invite body。Runtime 从 `offset - sizeof(ushort)` 执行当前下行结构化解包。业务 outbound 模板、client-driver fallback 与旧 Bot 协议兼容均已删除（M4/M5）。
5. **Agent 状态** — `BotRelayFarmNative` / `BotSessionState`；**禁止** Bot 写 `ReplyMessageShared`（M6）。
6. **匹配** — `BotMatchGuard` 禁止 Bot↔Bot（M7）。
7. **进关授权** — `LoginManager.__Start` 在 `Waiting` 边界单次发送 MatchStart；Bot 仅当场消费通过 Join/Match 当前代次门禁的消息。早到/旧代次消息拒绝且不缓存；Play/ChapterStage 作为当前真人协议由下行层完整解析和消费，但不生成 Bot 进关事件。
8. **单一状态** — 本次真实 server hello 后的 `Connected` 是唯一链路就绪门禁；`session.matchID` 是唯一匹配绑定，非零 ID 提交后不可被另一非零 ID 覆盖，Server→Bot 的 Mismatch 通知仅取消相同当前代次；MatchToRead 到达即释放 outstanding matchingSlot。
9. **严格格式** — Invite 只接受当前完整 app 与本次 Capture 的唯一 framing；录像只接受 TRBT v2。旧 Invite body/offset 与 TRBT v1 测试应删除，不得作为兼容门禁。

### 4.2 Bot 侧（与发布一致）

PlayMode 中 Bot 仍走：

```
当前完整 Server→Bot Invite + 本次 Capture framing → DrainInbound → PendingInvite → Agent 写 inject queue
→ Server Handler → RouteSend → bot vport
```

禁止：PlayMode 专用捷径直接改 Farm 状态冒充 Join 成功，把业务 app 伪装成 UTP wire，为旧 Bot body/offset/TRBT v1 保留兼容用例，或为 MatchStart 早到消息保留缓存；EndToEnd 必须经 inject queue、Server Handler 与显式的 Server ack / Inbox 路径验证。

### 4.5 录像素材门禁

录制只从显式开启的 completed-`EndWrite` journal 取数。journal 随每个非空 EndWrite 原子保存 payload、全局 sequence 和 producer `epoch + double timestamp`，与 transport 的 Apply/Clear、send/retry cursor 独立。禁止恢复 transport 槽扫描/per-slot cursor，也禁止对积压批次插值、均摊或补时间；缺失 PlayerProperty 时只能报错，不能从 SharedStatic、本地属性或 fixture 合成/补写。

点击「完成录制」后，Editor 必须先完成 producer jobs、final drain 和 clean journal end，再调用 `LevelRecordingFileValidator.ValidateSession`。出现 `captureError` 或任一 Audit Error 时，在弹出保存路径和写文件之前阻止保存；Serializer 还须在创建/截断目标文件之前校验 duration、时间戳和 payload。失败录制不能覆盖已有文件。

发布回放端只负责忠实消费 **TRBT v2** 时间轴：`Read` / `ReadHeader` 对 v1、未知版本或损坏文件 fail-close，不做兼容迁移。每个 Server Tick 注入当时已经到期的全部 gameplay 帧，同一时间戳批次不得被固定条数限流拆开。异常素材统一通过 Editor 菜单 `Tools/MultiplayerBot/Recording Batch Audit` 检测：

- `NonMonotonicTimestamps`：任意时间戳倒退，Error。
- `CollapsedMoveTimestamps`：同一 timestamp 的 Move 总数或 byte-identical Move 数 `>=8`，Error。
- `DuplicateSameTickMove`：2–7 条 byte-identical Move 同 timestamp，Warning。
- 同 timestamp 的多条不同 payload Move：合法，不作为塌缩。
- `LargeMoveGap`：相邻 Move 超过 15 秒，Warning，需结合其他 gameplay 帧确认真实静止区间。

超出 relay packet 容量、缺失/不可解析 PlayerProperty 等仍是 Error。旧录像的倒退、空洞或坍塌无法由回放端可靠恢复，必须重录；不能依靠运行时慢放、插值、丢帧或限流掩盖。

生产配置必须保持 `BotRelayDefines.VerboseTelemetry=false`。基于 80–160B 长度猜 Invite 的 `InviteShell RouteSend/Drain` 遥测及其测试已经删除；长度永远不是 Invite 类型判据，Move/Camera 也会命中。通用逐包 `RouteSend peeled` 仍只允许在显式诊断时开启，生产常开会以日志和完整堆栈扰动 Server Tick。发布日志只保留回放开始与完成汇总，完成汇总中的 `finalTickAdvanced/finalTickInjected/delta/playback` 用于识别异常追赶或提前耗尽。

## 5. 改代码检查清单

**改 `Relay/`（发布）前**

- [ ] 是否需要 Editor 才能编译/运行？→ 移到 `Editor/`  
- [ ] 是否新增 Catalog 槽位只为 PlayMode？→ 禁止  
- [ ] 是否让 Bot 写 `ReplyMessageShared`？→ 禁止（M6）  
- [ ] 是否第二颗热路径 `NetworkDriver`？→ 禁止（P1–P3）  
- [ ] 是否新增 relay-ready/match-paired 镜像、Invite 旧格式或多 offset fallback？→ 禁止

**改 `Editor/` 测试前**

- [ ] 是否仍走 `World.Update` + PopEvents？  
- [ ] Host 行为是否更接近 Manual Play（长期：NetworkClient）？  
- [ ] TearDown 是否 `ResetDiagnostics`（含 `BotRelayHostTestClient.ResetSessionState`）？  
- [ ] 是否覆盖真实 hello 才置 `Connected`、应用层 Connect 精确恢复远端在线状态且不冒充 UTP 握手、MatchToRead 立即释放 outstanding matchingSlot、不同非零 matchID 不可覆盖、下行 Mismatch 仅取消当前代次、Invite 完整 EOF 与 TRBT v1 拒绝？

**改 Common Server 注入/发送缓冲前**

- [ ] 同 userID 的注入是否仍保持原始顺序串行，不同 userID 才并行？
- [ ] Disconnect 后 connections / sendBuffers / targets 是否按同一 ordered `RemoveAt` 语义对齐？
- [ ] retry `Append(index)` 是否包含 index 指向的第一条未发送消息？
- [ ] opt-in EndWrite journal 是否仍与 Apply/Clear、send/retry cursor 独立，并保存同一提交点的 payload/sequence/stamp？
- [ ] recording inactive 时是否仍只有常量级分支，不分配 journal？
- [ ] `ZG.Entities.Networking.Common.Tests`（含 EndWrite capture suite）是否全绿？

**改录制/审计前**

- [ ] producer 时间是否仍以 `Time.unscaledTimeAsDouble` 的相对 `double` + epoch 发布，写 v2 时才转换为 float？
- [ ] 是否没有批次插值、transport 槽游标、PlayerProperty 合成/补写？
- [ ] 保存按钮与 Batch Audit 是否复用 `ValidateSession` 同一规则路径，Serializer 是否在覆盖目标文件前预检？
- [ ] `>=8` 同 timestamp Move 为 Error、2–7 相同 payload 为 Warning、同帧不同 payload 合法的边界测试是否仍在？
