#功能目标
1. 实现组队&匹配这两个联机玩法的机器人，模拟真实玩家行为。
2. 实现配合1使用的关卡录制工具。

#游戏联机玩法基本运作机制说明
1. LoginManager.ApplyLevel是游戏每个关卡的入口。
2. 组队&匹配这两个玩法都为2人的开房间式联机玩法。
3. 组队和匹配这两个玩法都可以邀请其它玩家共同进入关卡，但匹配玩法也可以先申请匹配，匹配成功（如果此时也有其它玩家申请匹配）后，组成临时的队伍进入游戏。
4. LevelPlayerShared<LocalPlayer>为本机玩家数据，LevelPlayerShared<RemotePlayer>为被邀请的玩家数据。
5. 其他联机相关机制请重点关注ZGUP Terminator包的ClientData、ReplyMessageSystem及ZGUP Entities Networking Common包去理解。

#机器人需求
1. 玩家发送世界组队邀请后，一定时间（可作为配置参数，比如5-10秒的随机范围）后无其它玩家响应，则自动派发机器人加入队伍。
2. 真人进入 Server `matchIDs` 后，Farm 等待配置的随机时长，再从空闲机器人中选择段位最接近者申请匹配；机器人不主动周期进池，且**不得** Bot 与 Bot 互配（见 [联机机器人-技术设计.md §3.6](./联机机器人-技术设计.md)）。
3. 机器人使用的 userID 通过 `BotConfig.botProfiles` 配置（按 userID 配表，非运行时随机）。`userID` 同时是 Server identity 与 Bot 下行虚拟端口路由键，因此必须非零且在整个账号池中唯一；运行时在创建 Connect wire/agent 前保留每个 userID 的第一项并忽略重复/零值项，同时输出明确告警。
4. 机器人进入关卡后，组队和匹配统一按 **`StreamingAssets/Recordings/{StageID}` → `{LevelID}_{stage}` → `{Path.GetFileName(matchStart.sceneName)}`** 选取录制（同目录多条则随机），目录优先级不因流程分叉。Bot 的唯一进关描述来自真人 `LoginManager.__Start` 在 `Waiting` 边界单次发送的 `ClientMessageMatchStart`：普通组队 `matchID=0`，匹配为与当前 `MatchToRead` 相同的非零 matchID。Bot 状态层不得从 `ClientMessagePlay`、`ChapterStage`、远端 `Status`、录像 Header 或本地客户端 ID 取得或补齐 Stage/level/scene tuple；Play/ChapterStage 仍是当前真人协议，Bot 协议层须完整解析并消费，但不生成进关事件。匹配先发送登录 `PlayerProperty`（Status 保持 0），下一 Tick 再发送非零 Status 并启动回放。三类精确键都缺失，或所选录像没有可用的首个 `PlayerProperty` / 该帧注入失败时，必须 fail-closed：不得发送非零 Status，也不得启动回放。详见 [联机机器人-技术设计.md §4.3](./联机机器人-技术设计.md)。
5. `MatchStart` 只从 `LoginManager.__Start` 的 `Waiting` 边界单次发送。Bot 对完整 type=24 SendRelay app 做结构校验并原样处理，`matchID=0` 必须作为合法普通组队描述保留。状态层只在对应代次已经成立时直接消费：普通组队须先由 `Join` 确认当前 squad/Host，匹配须先由 `MatchToRead` 把当前非零 ID 写入 `session.matchID`；任何早到、跨队、跨邀请或 matchID 不符的 MatchStart 都立即拒绝，**不做任何 pending/乱序缓存**。非零 `session.matchID` 一经提交即代表当前唯一代次：相同 ID 重复消息只能幂等处理，不同非零 ID 不得覆盖；Server→Bot 的 `Mismatch` 通知也只能取消相同的当前代次，旧/外来 Mismatch 必须忽略。禁止扫描 level/scene 字符串内部后误判成其他协议；可靠通道不增加应用层循环重发，也不保留旧 Bot 协议 fallback。
6. 玩家完成关卡后机器人离队。

#机器人实现机制
1. **生产路径**：Bot 与 ReplyServer **同进程共部署**（`Server.unity`），单进程内 Farm 模拟多个虚拟客户端（每 Bot 一个 `virtualPort`），**不是**多个独立进程各自连 Server。详见 [联机机器人-文档索引.md](./联机机器人-文档索引.md)。
2. 机器人不依赖客户端资源（模型、场景等），纯逻辑运作。
3. **传输边界**：原始 UTP Connect 握手 / 必要 link ACK 走 Capture 得到的 UTP wire；Connect 后所有 Bot→Server 业务协议只通过 ReplyServer 已开放的注入 API 进入既有 Handler。Server→Bot 保留 UTP 下行的结构化 PopEvents 解包；WireCatalog 只保存握手 Connect/server hello/link ACK 与当前入站定位，禁止保存、猜测或重建任何业务 outbound wire。应用层 `NetworkRelayMessageType.Connect(type=0)` 是当前远端成员重连状态，必须按 `[Connect, channelFlag, userID] + EOF` 精确解析，与原始 UTP 握手分开。
4. **单一事实源**：发出 UTP Connect 只表示 `ConnectRequested`，不会提前宣告链路可用；只有收到本次连接真实 server hello 才设置 `Connected`，它是业务注册/匹配唯一的链路就绪门禁。匹配绑定只认 `session.matchID`：0 为未匹配，非零值只由 `MatchToRead` 提交且在当前代次内不可被另一非零值覆盖；只有同 matchID 的下行 `Mismatch` 通知可以取消它，不存在第二份布尔配对状态。Farm matchingSlot 只覆盖尚未得到 MatchToRead 的 outstanding MatchToSend，结果到达即释放，不等待临时 squad Join。
5. **Invite 严格协议**：只接受当前完整 SendRelay app：`Invite(104) + relayType + senderID`，字节对齐后依次读取 `levelID + stage + channel + FixedString512 + FixedBytes80`，并要求恰好读到 EOF。禁止旧 body、截断 Header、连续位流、任意 offset、junk/文本恢复或字段改写。
6. 尽可能高性能，不依赖别的系统；热路径为 ECS + Job + Transport Catalog + Server inject queue（见架构约束）。

#关卡录制工具需求
1. 只能在Editor下运行。包含录制并保存，读取录制文件，回放录制文件功能。
2. 先运行Play Mode，点击录制后重新加载当前场景，开始录制，同时GUI显示“完成录制“按钮。
3. 完成录制后弹出保存到文件。
4. 回放时，读取一个录制好的文件，重新加载当前场景，以机器人的方式回放。

#关卡录制工具实现机制
1. 先分析理解游戏多人联机的运作原理，当联机时，ReplyMessageSystem的LevelPlayerShared<RemotePlayer>.isOnline && LevelPlayerShared<RemotePlayer>.channelStatus == LevelPlayerShared<LocalPlayer>.channelStatus条件成立。
2. 录制开始时显式开启 `NetworkClientSendBuffer` 的 completed-`EndWrite` journal；现有 PlayerProperty / Move / Camera / Damage / SelectSkill 发送路径保持不变，每次非空 EndWrite 原子记录 payload、全局 sequence 与 producer `epoch + double timestamp`。
3. 录制 ECS 系统只从独立 journal 按提交顺序 Peek/复制/Consume。journal 与 transport 的 Apply/Clear、send/retry cursor 独立；禁止扫描 pending slot、维护 per-slot 游标或对积压批次插值/补时间。
4. 只能保存真实 EndWrite。缺失 PlayerProperty、journal fault、时间戳倒退等情况必须 fail-closed，禁止从 SharedStatic、本地属性或 fixture 合成/补写录制帧。
5. 「完成录制」先对内存 Session 执行与 Batch Audit 相同的硬门禁，任一 Error 都不得弹出保存路径或写文件；Serializer 还必须在覆盖目标文件前做结构预检。
6. 当前二进制格式只接受 `TRBT v2`；v1、未知版本或损坏文件在 `Read` / `ReadHeader` 时 fail-close，需重新录制，不做兼容迁移。Audit 中同 timestamp Move 总数或相同 payload 数 `>=8` 为 Error，2–7 条相同 payload 为 Warning，同帧不同 payload 合法；旧倒退/坍塌素材必须重录。

#原则
1. **代码归属**：机器人现行实现位于 `ZGUPTerminator`；运行时、录制、Editor 测试与文档均直接在包内维护，`BotConfig.asset` 留在使用方工程、不得放入包。独立 Headless 路径已彻底下线。其他 ZGUP 包仍须先评估再修改。`AddDriver`/`ListenDriver` 属已落地的底层 API，见 [落地方案 §4](./联机机器人-落地方案.md)。
2. **Server 零分叉**：Relay/Identity/Handler/撮合逻辑不因 Bot 特化；Bot 侧适配。
3. 先尽可能理解工程及游戏运作原理；有理解不够清晰的先提问，完善文档，再落实。
4. 始终围绕目标为核心。
5. 文档放在包内 `Documentation~/MultiplayerBot/`；代码按程序集拆在包内 `Terminator.MultiplayerBot*` 目录，架构权威见 [联机机器人-架构约束.md](./联机机器人-架构约束.md)。
6. 代码风格参考 ZGUP Terminator 包。

#EditMode 自测（邀请链路）
手动 Play 联调前，先跑 Bot 的 **EditMode `Regression`**（`Terminator.MultiplayerBot.Tests` 与 `Terminator.MultiplayerBot.Recording.Tests`）：
- 必须覆盖：Server→Bot PopEvents 分帧、邀请 `Mismatch→Join` 的 app-layer inject、`ApplyMatch`、`PlayerProperty` 及大于旧 500B 上限的录制帧保真、录制容量校验。
- 若 Console 有编译错误或 Domain Reload 尚未结束，先等待 Editor 稳定；不得把旧 UTP outbound 槽、固定 wire 长度或仅 queue 有数据当作业务通过。
- EditMode 通过后再跑 `category=PlayMode` 的单会话自动门禁；门禁在一次 `Server.unity` Play 会话内依次覆盖 6 个行为点，只有全绿才进行人工邀请/进关复核。详细流程见 [联机机器人-架构约束.md](./联机机器人-架构约束.md#61-playmode-验收模拟真人操作交付门禁)。

**编解码原则**（PopEvents 分帧 + `BotRelayMessageUtility` + Regression）：见 [联机机器人-传输编解码约束.md](./联机机器人-传输编解码约束.md)。
