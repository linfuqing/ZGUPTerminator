## 1. 核心目标（一句话）

**Bot 与 ReplyServer 同进程共部署：仅 1 个挂入 `MultiNetworkDriver` 的 Listen Driver。Bot 仅以 UTP wire 建立 Connect / 维护必要 link 层；Connect 后的 Bot→Server 业务消息经 Server 已开放注入 API 进入同一 `NetworkRelayServerHandler.Read`，Server→Bot 仍经 `RouteSend`、UTP 结构化解包与 Inbox；Bot 侧不对任何 driver 单独 `ScheduleUpdate`。**

---

## 2. 必须满足

| # | 约束 | 说明 |
|---|------|------|
| M1 | **唯一热路径 driver** | 只有 Bot Listen Driver 经 `NetworkRelayServer.AddDriver` 挂入 Server；**仅**由 `NetworkRelayServerSystem` / `NetworkServer.Schedule` 驱动其 `ScheduleUpdate`。 |
| M2 | **Interface 伪装远端** | 每 Bot 映射为独立 `virtualPort`。仅 Connect / link ACK 经 `EnqueueToListen(virtualPort, utpWire)` 进入 Listen；Connect 后 Bot→Server 业务协议经 `BotRelayInjectQueue` → `NetworkRelayServerInjectSingleton` → `NetworkRelayServerHandler.Read` 投递。Server→Bot 经 `RouteSend` 进入 `virtualPort` channel，PostTick `TryDequeueToBot` → `DrainInbound` → `BotRelaySlotInbox`；下行 ClientMessage / ReplyMessage 没有第二套镜像。 |
| M3 | **Server 零分叉** | Relay/Identity/Handler/撮合 **不为 Bot 特化**；Accept、Handler.Read、SendBuffer 与真人一致。包级暴露（如 `AddDriver`）属负责人评估后的改动，见 [落地方案 §4](./联机机器人-落地方案.md)。 |
| M4 | **传输边界：Connect 用 UTP，业务用 Server 注入** | `EnqueueToListen` 只允许 Connect 捕获线和 link ACK 模板等 **确知的 UTP wire**；禁止手工 prepend、按 offset 拼 UTP，或把裸 app / `FrameForTransport` 当 wire 注入。Connect 后的 `Status`、`MatchToSend`、`Join`、`ApplyMatch`、`Mismatch`、`Leave`、`PlayerProperty` 与回放帧，必须按 ZGUP app 编码写入 `BotRelayInjectQueue`，由 `BotRelayInjectFlattenSystem` 转入 `NetworkRelayServerInjectSingleton`，再由 Server 的既有 Handler 处理。生产 Agent / Replay 系统把注入队列视为必备依赖：队列或 Server inject singleton 不存在时必须停更并暴露配置错误，**不得**静默退回业务 UTP wire。它不是改 Server 业务逻辑，也不是绕过 Handler；它是不用猜 UTP 的正式上行入口。 |
| M5 | **Tick 分工** | PreTick：仅 Connect wire / 必要 link ACK 注入；Server System：唯一 `ScheduleUpdate` 与注入队列消费；PostTick：下行 Drain → Inbox → Agent。Agent / Replay 产生的上行业务消息写入 inject queue，下一帧 `BotRelayInjectFlattenSystem` 在 Server System 前统一投递。 |
| M6 | **每 Bot 本地状态** | 协议/业务状态在 `BotRelayFarmNative` / `BotSessionState`；不写 `ReplyMessageShared` 等 SharedStatic。 |
| M7 | **禁止 Bot vs Bot / 抢同一队** | 不改 Server 撮合；Bot 侧保持两类原子租约：**匹配槽**限制同时仅一台 Bot 入匹配池；**队伍租约按 squadID 去重**，同一外部 Invite 仅一台 Bot 接受，但不同真人 squad 可由不同空闲 Bot 并发服务，最多受 Farm Bot 数量限制。外部 Invite 包括世界 `Public` 和指定 Bot userID 的 `Private`；`Squad` channel relay 是队内流量，不能触发空闲 Bot 加队。配对后 `remoteUserID` 为 Bot 仍须 `Mismatch`/`SquadLeave`（`BotMatchGuard`）。每个 Bot 的 squad key 在该 Bot 经 `JoinFail`、显式 Server `Drop` 或 `Leave` 回到 `Idle` 时释放；同一 channel 的后续 Invite 是新事件，仍可由空闲/匹配 Bot 接受。 |

## 3. 明确禁止（曾出现偏差）

以下做法视为**偏离目标**，不得作为默认方案或「临时妥协」长期保留：

| 禁止项 | 典型错误形态 | 为何偏离 |
|--------|--------------|----------|
| **P1 第二颗 live NetworkDriver** | `BotRelayWireEncoderState.driver` 每帧 `ScheduleUpdate` / `BeginSend` / `PopEvent`（mirror encoder） | 在 Interface 外又跑一套 UTP 客户端，与「单 driver」矛盾 |
| **P2 第三颗 live UTP 栈** | `BotRelayEncodeIsland` 在热路径 `BeginSend` 并注入 live bot 的 `virtualPort` | 独立 session 的 wire 与 Accept session 不一致 → Disconnect |
| **P3 Client driver 热路径** | `BotRelayClientResources` + Pre/Post `ScheduleUpdate`（`BOT_RELAY_WIRE_FALLBACK`） | 仅作 **调试/对照**；`#define` 默认 **OFF**，不是交付目标 |
| **P4 Connect 双轨** | wire 模板注入 Accept + mirror `suppress Connect` 并行建 session | 两套 UTP session，出站/入站无法与 Accept 对齐 |
| **P5 改 Server/Relay 包** | 为 Bot 加 Handler 分支、SharedStatic 捷径 | 违反「不改 Relay 逻辑」原则 |
| **P6 按消息猜 wire/app 编解码** | 固定 offset、字节扫描猜 `ReplyMessageType`、Play 通了再补 heuristic；合成 fixture 冒充 live 抓包 | 每种消息重复劳动；ZGUP struct 扩充即失效；见 [传输编解码约束](./联机机器人-传输编解码约束.md) |
| **P7 混淆 Live Wire 槽位** | deferred Invite 写入 `wireLiveServerHello`；Join flush 复制 Invite listen shell 作 outbound；测试只比 `joinInj` 或固定 117B | session patch 失败或真人 `ReadFixedString512` 越界；见 §5.4 |

> **允许的唯一例外（Init-only，非热路径）**：初始化阶段可用 **一次性、采完即 Dispose** 的 ephemeral listen+client 采集 **Connect / server hello / link ACK** 等确知 UTP 模板；**不得**在 Pre/PostTick 对这类 driver 做每帧 Schedule。历史遗留的 Status / Match / Join 等 outbound 模板可暂留作兼容诊断，但不是业务投递的权威路径，后续清理须先完成注入链验收。

## 4. 正确数据路径

```
PreTick（BotRelayPreTickSystem）
  ConnectPending → EnqueueToListen(connectWire[0..connectClientWireCount))
  PumpLinkLayerAcks（仅必要 server→bot link 包 → 注入 ACK 模板回 Listen）

NetworkRelayServerSystem（唯一 driver ScheduleUpdate）
  Listen Receive → Accept → Handler.Read → SendBuffer → Listen Send
       ↓
  RouteSend → BotRelayManager（virtualPort channel）

PostTick（BotRelayPostTickSystem / Replay Jobs）
  TryDequeueToBot → 结构化 PopEvents walk → Inbox
       ↓
  BotAgentLogic / Replay → BotRelayInjectQueue

下一帧、Server System 前（BotRelayInjectFlattenSystem）
  BotRelayInjectQueue → NetworkRelayServerInjectSingleton → Handler.Read
```

**要点**：UTP 只在 **Connect / link 层和 Server→Bot 下行** 的 `BotRelayManager` / Interface 边界处理；不再为 Bot→Server 业务消息编码或猜解 UTP。
**App 层字段顺序以 ZGUP 为准**；上行用公开 Server 注入入口，下行只允许结构化 PopEvents framing walk，禁止按消息类型猜 offset — 详见 [联机机器人-传输编解码约束.md](./联机机器人-传输编解码约束.md)。

## 5. 模块职责（目标态）

| 模块 | 职责 | 热路径 |
|------|------|--------|
| `BotRelayNetworkInterface` | Listen 端 ScheduleReceive/Send，与 Manager 队列对接 | ✅ |
| `BotRelayManager` | virtualPort channel、Connect/link 的 `EnqueueToListen`、下行 `TryDequeueToBot` / `RouteSend` | ✅ |
| `BotRelayConnectWire` + **WireCatalog** | Init 采 Connect / hello / link ACK；下行结构化解包 / link ACK 回注。历史 outbound 壳仅兼容诊断，不能作为业务投递保证 | Init + ✅ |
| `BotRelayInjectQueue` + `BotRelayInjectFlattenSystem` | Connect 后 Bot→Server 全部业务 app 编码、排队、在 Server System 前转入 `NetworkRelayServerInjectSingleton` | ✅ |
| **`BotRelayWireCatalogHost`** | Runtime 只读托管 `BotRelayWireCatalogState`（见 §5.1）；ECS 实体仅挂 `BotRelayWireCatalogReadyTag` | ✅ |
| `BotRelayAgentSystem` | Pre/Post Tick，只调 Manager + Farm + Catalog（经 Host） | ✅ |
| `BotRelayWireEncoderHost` / `BotRelayEncodeIsland` | ~~mirror / live flush~~ | ❌ 应从热路径移除 |
| `BotRelayClientResources` | fallback client driver | ❌ 仅 `#define BOT_RELAY_WIRE_FALLBACK` |

### 5.1 WireCatalog 存储（Runtime，不可偏离）

**问题**：`BotRelayWireCatalogState` 内含多个内联 `BotRelayPacket`（约 1.5KB×12），整 struct 约 **17KB**，超过 ECS chunk 上限（约 16KB）。若作为 `IComponentData` 挂到 Bot World 实体会触发 `Archetype too large to fit in chunk`。

**合规布局**：

| 层级 | 内容 | 说明 |
|------|------|------|
| **逻辑类型** | `BotRelayWireCatalogState` | 仍作为 catalog 的数据结构（模板 + `NativeList` 映射）；**不得**整包 `SetComponentData` 到实体 |
| **Runtime 托管** | `BotRelayWireCatalogHost` | Init 成功后 `Publish(in catalog)`；Pre/PostTick 经 `ref readonly Host.Catalog` 只读访问；Shutdown 时 `Host.Dispose()` |
| **ECS 标记** | `BotRelayWireCatalogReadyTag` | 空 tag，表示 Host 已 Publish；Agent 查询 `RequireForUpdate`，**不**承载模板字节 |
| **Bot World 实体组件** | `BotRelayWorldTag`、`BotRelayHubState`、`BotRelayFarmConfig`、`BotRelayFarmNative`、`BotReplayCatalog` | 不含 WireCatalog 字节 |

**Init 路径（仅一次，非热路径）**：

1. `BotRelayWireCatalog.Capture` — ephemeral listen+client 采模板（采完 Dispose；pump 时 drain 防 `Resetting event queue`）。
2. `BotRelayWorld` — `InitContext`（堆上）持有 `NetworkDriver`，避免栈上 16KB `InvalidProgramException`；Init `AddDriver` 经 `NetworkRelayServerManager.server`（ref 写 ECS），禁止热路径 `GetComponentData<NetworkRelayServer>` 按值拷贝。
3. `BotRelayFarmSpawner` — 创建 World 实体 → `Host.Publish` → 挂上 `BotRelayWireCatalogReadyTag`。

**热路径读法**（当前）：

```csharp
// PreTick 仅做 Connect / link；业务上行由 PostTick 的注入队列投递。
BotRelayBurstWireOps.PreTickAgent(index, ref farm, ref manager, ref catalog);
BotRelayInjectOps.InjectControlMessage(ref injectWriter, userID, type, arg, hasArg);
```

**后续 Burst / 无 `Complete()` 演进（规划，非当前阻塞）**：

- 模板迁入 **`BlobAssetReference`** 或 Persistent **`NativeArray`** 只读视图；Host 仅持 blob 句柄与生命周期。
- Job 入参携带 `ReadOnly` blob / native 视图，**禁止** Burst 内读 static managed Host。
- 与本次 Host 方案**兼容**：Publish 时写 blob，热路径从 blob 读；`BotRelayWireCatalogReadyTag` 保留作 ECS 就绪门闩。
- Init 侧 `ScheduleUpdate().Complete()`、`world.Update()`（AddDriver）**不在**热路径并行化范围内。

**禁止**：

- 为「放回 ECS」把 `BotRelayWireCatalogState` 再挂为 `IComponentData`（必 chunk 溢出）。
- 每 Bot 复制一份完整 catalog（模板只读共享即可）。

### 5.2 热路径优先级（性能 / 安全 / Dispose）

**优先级（高 → 低）**：

1. **帧性能** — Farm Tick / Replay / Wire 收发必须走 **Burst + Job 链**（`IJob` / `IJobParallelFor`）；**禁止**为 Editor 停服或 Play 退出时的 Dispose 警告，把热路径改回主线程同步循环。
2. **内存与并发安全** — 只读数据用 **`BlobAssetReference` + `[ReadOnly]`**（WireCatalog、Replay Catalog）；可写状态用 **按 agent 分区的 `NativeArray`**；Job 间共享写（如 `BotRelayManager` 队列）须 **bucket 锁** + `[NativeDisableParallelForRestriction]`，**禁止**裸并行写同一容器。
3. **Dispose / 停服** — 仅发生在 **Shutdown / ExitingPlayMode**；允许在停服路径 `JobHandle.Complete()` / `CompleteAllTrackedJobs()`，**不得在** Wire 热路径 per-frame `Complete()`。

**禁止（曾出现偏差）**：

| 禁止项 | 错误形态 | 正确做法 |
|--------|----------|----------|
| **D1 热路径牺牲 Job** | 为消除 Replay Dispose 警告，把 `ReplayTickJob` 改为主线程 `for` | 保持 Job；Catalog 改 Blob；Shutdown 时 `CompletePending` |
| **D2 热路径 Complete** | Pre/PostTick 或 Manager 访问每帧 `Complete()` | Job 链 + `ManagerAccessHandle` 串联 |
| **D3 可写 Native 进 Job 无标记** | 并行 Job 写 `NativeList` 未 `[NativeDisableParallelForRestriction]` | 见 §5.3；或保持串行 `IJob` |

**安全约定**：

- 尽量 **不用 `unsafe`**；保留场景见 `.cursor/rules/unity-project.mdc` §2。
- Job 不持有 **已 Dispose 的 `NativeArray` 所有权**；Replay / Wire 只读视图用 **Blob 句柄**（Init 构建，Runtime 只读）。
- 跨 agent 原子状态禁止放 plain `int` 字段（并行 Job 按值拷贝会失效）。匹配使用长度 1 的 `matchingSlotOwner + Interlocked`，只覆盖入匹配池；队伍使用长度 1 的 `squadSlotLock` 保护每 Agent 的 `squadSlotSquadKeys`，以 `squadInviteID + 1` 为 key 去重。同 key 只允许一台 Bot，不同 key 可并发；各 key 持有至对应 Bot 经 `JoinFail`/`Drop`/`Leave` 转回 `Idle`。

### 5.3 Farm Tick Job 链（当前）

| 阶段 | Job | 并行 | 说明 |
|------|-----|------|------|
| PreTick | `BotRelayPreTickBurstJob` | `IJobParallelFor` | Connect 注入（**Spawn 预分配 `virtualPort`**）与必要 link ACK；不 flush 业务 outbound |
| Post Drain | `BotRelayPostDrainBurstJob` | `IJobParallelFor` | 每 agent  dequeue 自有 virtualPort；Manager bucket 锁 |
| Post Agent | `BotRelayPostAgentJob` | `IJobParallelFor` | Inbox + `BotAgentLogic`；业务消息写 `BotRelayInjectQueue`，无 Manager |
| Post Flush | `BotRelayPostFlushBurstJob` | `IJobParallelFor` | 仅 PumpLinkLayerAcks；不 flush 业务 outbound |
| 下一帧 Server 前 | `BotRelayInjectFlattenSystem` | `ISystem` | 把生产者队列搬入 `NetworkRelayServerInjectSingleton`，由既有 Handler.Read 消费 |
| Replay | `BotRelayReplayTickSystem.ReplayTickJob` | 串行 `IJob` | 读 `[ReadOnly] NativeArray<BotReplayCatalogEntry>`；Shutdown `CompletePending` |

**Replay Catalog**：Init 时 `BotReplayCatalogBuilder` 构建 **`Persistent NativeArray<BotReplayCatalogEntry>`**（每条只含从目录解析的 `userStageID`、`levelID` / `stageIndex` 或 `sceneName` + `recording` Blob）。可加载路径是 `StreamingAssets/Recordings/{userStageID}/`、`{levelID}_{stageIndex}/` 或 `{sceneName}/`；组队与匹配 lookup 都严格按该顺序，scene 键是 `Path.GetFileName(play.sceneName)`。普通组队的 `play` 来自 Host `ClientMessagePlay`；匹配的 `play` 由 `LoginManager.ApplyStart` 发出的 `ClientMessageMatchStart` 原样转换，同时取得 Register 后的服务器 UserStage ID。TRBT Header 的 `userStageID` / `levelID` / `stageIndex` / `sceneName` 均是录制客户端元数据，**不得**用于 catalog lookup 或任何协议注入。三种精确键都未命中时不得以同 Level 其他 stage、其他 scene 或任意录像兜底。**不可**整表迁入 `BlobArray`（Unity Blob 禁止嵌套 `BlobAssetReference` 指针）。Runtime Job 以 **`[ReadOnly]`** 引用该数组；Dispose 仅在 Shutdown 且 **`CompleteReplayTick` 之后**。

**virtualPort 预分配**：`BotRelayFarmSpawner` 在首帧 Tick 前调用 `BotRelaySlotOps.AssignVirtualPortsAtSpawn`（主线程、`AllocateVirtualPortBurst`）；PreTick Job **不得**再写 port map。`TryDisconnect` 保留 `virtualPort`（Farm 生命周期内 channel 稳定）。

### 5.4 Connect / hello 状态不变量与旧 outbound 壳（不可偏离）

`wireLiveServerHello` 只承载 Connect 后的 server hello，用于 Connect / link 层状态对齐；任何含 Invite、Match、Join 等 app payload 的下行大包都不得覆盖它。`wireLiveJoinListenShell` 只可保存这类下行 shell 供 PopEvents 诊断，绝不能被当作上行 Join 壳。

**关键变化（2026-07-22）**：Status、MatchToSend、Join、ApplyMatch、Mismatch、Leave、PlayerProperty 与回放帧不再依赖 `TryApplySessionPatch` / `TryEmbedLiveApp` / `TryComposePipelineListenUtpWire` 投递。它们的正式路径是 `BotRelayInjectQueue` → `NetworkRelayServerInjectSingleton` → Server Handler。生产 Job 链已不再调度 `FlushOutbound`；历史 outbound 模板、Join shell 断言和 `FlushOutbound` 本身仅保留给无注入测试回退/迁移审计，待全链路验通后删除，不得作为功能成功条件或新的实现依赖。

**Connect 身份不变量（2026-07-22）**：UTP Connect payload 含 `ClientHeader`，`virtualPort` 只区分虚拟端点，不能替代身份。初始化必须为每个 Bot 独立 Capture Connect 握手，并在 `BotRelayCatalogBlob.agentConnectClientWireRanges` 中按 agent 保存；PreTick 仅注入本 agent 的握手 wire。若复用 `profiles[0]` 的 wire，Server 会把多个 virtualPort 注册为同一 userID，后续被邀请 Bot 虽能收到下行邀请，却没有可供 Join 的 Server identity。

**Server Join 门禁仍有效**：`NetworkRelayServerIdentity.Join` 在 `match != 0` 时静默失败；Bot 在 Join 前必须先经注入路径投递 `Mismatch` 清除 server match。Spawn 的 `nextIdleMatchTime=∞` 仍用于避免 bot 启动即占用 match 槽。

**两条匹配路径的阶段边界（2026-07-29，不可推断）**：预组队路径在撮合前会收到 `ClientMessageType.ApplyMatch`，Bot 只回同类型消息表示同意，队长随后才发 `MatchToSend`；单人撮合形成临时队伍时没有 `ApplyMatch` 阶段，直接等待撮合成功。`NetworkRelayMessageType.Create/Join` 在两条路径中都只确认频道成员关系，不能写 `BotAgentState.matchPaired`。处理 Join 确认时必须由状态迁移同步提交 `session.channel`，不得只依赖 Inbox 的前置副作用；`InSquad + CHANNEL_NULL` 属非法中间态。预组队路径即使收到非零 `ChapterStage`，在 `MatchToRead` 前本地 `channelStatus` 仍必须保持 0，ApplyMatch 回复旁不得夹带 Status；普通组队只有 Host `ClientMessagePlay` 可以授权启动回放握手。唯一共同且权威的匹配成功事件是 Server 下发的 `ClientMessageMatchToRead`（relay `Match`）；只有该事件可以置 `matchPaired=true` 并进入 `Register + ApplyStart` 等价流程，迟到的 `ApplyMatch` 必须忽略。Match 是新的 Stage 代际边界：先清除 Match 前的 target/lastSeen/remote Status/PlayerProperty 就绪状态，然后等待真人 `LoginManager.ApplyStart` 广播 `ClientMessageMatchStart(matchID,userStageID,isRestart,levelID,stage,levelName,sceneName)`。该消息的 `userStageID` 来自 `__stageIDs[(levelID,stage)]`，其余字段来自本次 ApplyStart；Bot 不再维护 `rankedMatchStageIDs` / `rankedMatchScenes`，也不从 `Match.level`、录像 Header、本地 `UserDataMain` 或编号规律猜值。Bot 收到与当前 matchID 一致的描述后分两 Tick：先仅发送录制首个 `PlayerProperty` 且保持 `Status=0`，下一 Tick 再发送 `PlayerProperty + Status(stageID)` 并启动回放。真人 Host 的登录等待允许“同一 Stage 的 Status 先于 PlayerProperty”并在 Joined 后继续，因而匹配无需广播 `Play`；`LoginManager.__Start` 仅在 `match==0` 的普通组队路径发送 `Play`。录像或 PlayerProperty 缺失必须 fail-closed。进关后不得追加 `Status(0)`；清零只属于真正的 Leave/Mismatch。

**MatchStart 显式类型优先（2026-07-30）**：Server→Bot 的 PopEvents payload 若 offset 0 已完整解析为 `ClientMessageMatchStart(type=24)`，必须校验完整 SendRelay envelope/body 后原样提交；不得先做 inner-offset 猜测。`levelName/sceneName` 是任意 UTF-8 字节，扫描其内部会产生伪造的合法控制类型。inner-offset 扫描只服务于确实带内部 envelope 的历史壳，不得覆盖显式且结构完整的新协议。该 Channel 是可靠通道，发送端保持 ApplyStart 单次发送，不以循环重发掩盖接收端解码错误。

**Job 调用链 helper 不得生成独立 Burst 直调入口（2026-07-26）**：`BotReplayLogic.Stop/Tick` 只允许作为普通静态 helper；`Stop` 在 `BotRelayPostAgentJob → BotAgentLogic` 下由外层 Burst Job 传递编译，在 `BotRelayReplayLoadJob` 等 managed 调用方下直接执行；`Tick` 由 `ReplayTickJob` 传递编译。方法级 `[BurstCompile]` 会额外生成 `$BurstDirectCall` 包装，Linux/Mono 在 managed Job fallback 中解析该包装时会因 `$BurstManaged` 缺少 `MonoPInvokeCallback` 抛异常。尤其 `SquadJoin` 已先清除 pending invite、写入 channel，随后调用 `ClearPlayStageState → Stop`，异常会阻断最后的 `InSquad` 迁移，形成不可接受的半提交状态。门禁 `ReplayJobHelpers_DoNotExposeStandaloneBurstDirectCallEntrypoints` 必须保持全绿；Linux 发布包还须确认日志中不再出现 `Stop$BurstManaged` / `Stop$BurstDirectCall`，且一次 Join 确认后稳定进入 `InSquad`。

**测试原则**：验证 Connect 时检查 UTP template / hello 不变量；验证业务消息时检查 inject queue 被 drain、Server Handler 的结果状态和下行 ack。禁止以固定 wire 长度、`joinInj` 计数或任意 outbound UTP 字节形状作为 Join 成功证明。

### 5.5 Server→Bot 空管线 + per-userID 路由（不可偏离）

**问题（`NetworkSendMessage: -5` 根因，已验证）**：Server 默认对每条连接建 `[Fragmentation, ReliableSequenced]` 管线。`ReliableSequenced` 的**发送窗口需对端 ACK 才能推进**，而单 Driver 的 bot **不产生 UTP link 层 ACK**（无 live 客户端栈）；窗口填满后 server→bot 发送队列饱和 → `NetworkSendQueueFull(-5)` 洪流。同时可靠管线**头部变长**，使 `inboundAppPayloadOffset` 不稳定，被迫按消息「猜」payload 起点（违反 P6）。

**方案：bot 连接改走 UTP 空管线（no pipeline stages）**。

| 机制 | 做法 |
|------|------|
| **单一来源** | `BotRelayPipeline.Null`（= `default(NetworkPipeline)`）为所有 bot 连接唯一管线；命名/引用全岛对齐 |
| **per-userID 路由** | Spawn 后 `BotRelayFarmSpawner.__RouteBotsThroughNullPipeline` 写 `NetworkRelayServerInjectSingleton.pipelines[userID] = Null`；server 发送路径 `NetworkServerSendBuffer.Send` 解析 `pipelines.TryGetValue(userID) ? that : Pipeline`——**bot 走空管线，真人保留默认可靠+分片管线**（真人收 bot 消息不受影响） |
| **listen driver 计数不变量** | bot listen driver 挂入 server `MultiNetworkDriver` 需与 udp/ws driver **管线数一致**（否则 `AddDriver` 抛 "must have 1 pipelines, but has 0"）。`BotRelayPipeline.CreateServerMatchingPipeline` 建一条匹配的 `[Fragmentation, ReliableSequenced]` 仅满足计数/索引不变量；**bot 实际发送仍经 per-userID map 落到 `Null`** |
| **两级确定性解码** | inbound 只走 ①`catalog.inboundAppPayloadOffset` 定长剥离 → ②确定性 PopEvents framing walk（`TryExtractAppViaTransportFraming`）兜底；**删除**逐消息启发式扫描。改管线只需**重新抓包**自动重测该单一 offset，无需改码（解决 P6 可扩展性） |

**为何解决 -5 与「不好维护/留后患/无法扩展」三点**：空管线消除 server→bot 的 `ReliableSequenced` 发送窗口饱和；inbound 只做确定性 framing walk，不猜消息；而 **全部** Bot→Server 业务消息均经 App 层 inject 可靠投递，不再把 session 相关 UTP 组包当作可维护方案。管线变更时只需重验 Connect / 下行 framing，不需要为每个上行协议重抓包、补 offset。

**业务上行必须走 inject（不可偏离）**：`Status`、`MatchToSend`、`Join`、`ApplyMatch`、`Mismatch`、`SquadLeave`、`PlayerProperty` 以及回放 gameplay 帧都必须经 `BotRelayInjectQueue` 投递。`BotState.Leaving` 的 `SquadLeave` + `Status(0)` 尤其不能只写 outbound wire，否则 server 不会移除 bot，表现为完成关卡或房主离线后 bot 不离队。

**注入负载上限（2026-07-22）**：queue item 直接存 `BotRelayPacket`，上限与 relay app 一致为 `1472B`，不得再用 `FixedList512Bytes` 截断或拒绝合法录制帧。经 2026-07-23 校验，资源工程 `Terminator_Resource/Assets/StreamingAssets/Recordings` 的 106 个文件均可解析；规范目录可为 `{StageID}`、`{LevelID}_{stage}` 或真实 `sceneName`（如 `Level*.scene`），三类都会进入生产 catalog。**该目录被当前源码工程的 `Assets/.gitignore` 忽略，不能把资源工程盘点误称为当前工程已部署**。旧 500B 上限会静默丢失 `511–680B` 录制帧，可能导致 `PlayerProperty` 握手或进关动作回放缺失。超过 `1472B` 的未来录制必须在录制校验阶段报错/隔离，不能在生产回放中默默跳过。

**InLevel 期间真人退出 / 掉线的 -5：区分两个正交信号（不可混用）**：`channelFlag` 低位是 `NetworkRelayChannelFlag`（`Online` 在线位），`>> ShiftToStatus` 才是**关卡状态值**（stageID）。二者语义正交，`BotSessionState` 分别记录 `remoteChannelStatus`（状态值）与 `remoteOnline`（在线位）：

- **真人彻底离开关卡 / 返回大厅** → `remoteChannelStatus == 0`。这是**原设计的退队条件**（"channelStatus=0 才退队"）。`__TickChannelTracker` InLevel 分支据此（经 `InLevelReplayArmGraceSeconds` 3s + `RemoteLeaveWhileInLevelDebounceSeconds` 2s 去抖，滤掉房主每帧 Create/Join/Leave 重播抖动）转 `BotState.Leaving`。
- **房主明确移除 Bot** → Server 下发 `NetworkRelayMessageType.Drop`。它不是上述瞬时 `Leave` 重播，必须在 Agent 事件队列内立即停止回放、清空频道/Stage、回到 Idle 并释放该 Agent 的 `squadSlotSquadKeys`；同批后续 Invite 以清理后的状态重新竞争租约。
- **录像播放耗尽** → 只表示没有更多录制动作；**不得**把 `Playing` 清位当作出关，Bot 必须继续保持 `InLevel` 和队伍占用，并忽略新的世界/私有邀请，直到上述实时 `remoteChannelStatus == 0` 退队条件成立。邀请入口除检查状态外，还须以本地/远端 channel status、目标 StageID 和 replay runtime 作为状态同步延迟的守卫。
- **所有队伍统一离线宽限**：`Disconnect` 只将 `remoteOnline=false`，不得把没有携带 Status 的包误解为 `remoteChannelStatus=0`；大厅普通队、匹配临时队、关内队统一由 `BotAgentState.remoteOfflineSince` 计时。默认 `BotConfig.remoteOfflineLeaveTimeout=5s`（长于客户端 2s 自动重连等待）：宽限内重连则清零计时并保留队伍，超时则 Bot 转 `Leaving`，inject `SquadLeave + Status(0)` 释放占位。
- **匹配成功但真正进关前掉线**：同样走上述 5s 宽限，不应在通用 `NetworkRelayServerIdentity.Disconnect` 中立即 `Leave`；否则客户端只收到 `Leave` 而非可靠的匹配取消终态，可能与已启动的 Match/UI/ApplyStart 异步流程竞争。超时后由 Bot 主动离队完成清理。
- **-5 根因与统一处置**：server 对频道成员转发**不看** `isOnline`（`NetworkRelayServerIdentity.Relay(Channel)` 直写频道缓冲），因此真人退出（status 0）**或**掉线（offline）都会让 bot 的回放 gameplay 持续灌入不再 ACK 的真人可靠窗口 → `-5`。故只要真人"不在消费"（offline **或** status 0），`__TickChannelTracker` 立即置 `BotAgentRuntimeFlags.RemoteAbsentSuppressed`；`BotRelayReplayTickSystem.ReplayTickJob` 见此位**跳过 `BotReplayLogic.Tick`（暂停回放：不推进 playbackTime、不 inject）**。真人在宽限内重连即清位续播；offline 超过统一超时或 status 0 通过关卡离场去抖后，Bot 正式退队。
- **抑制必须"先确认在场"（避免进关看不到机器人）**：`remoteOnline` 默认 `false`，只在收到带 `Online` 位的 channel/status 消息时才置真。若直接以 `present==false` 抑制，进关瞬间（或该消息尚未刷新）就会误置 `RemoteAbsentSuppressed` → 回放永不推进 → **机器人隐身**。故用 `BotAgentState.remotePresenceSeen` 闩锁：仅在正向观测到 `present`（online 且 status≠0）后才允许后续缺席触发**流式抑制**；统一离线计时则以已知远端成员（`remoteUserID/remotePlayerCount`）为权威，不依赖该闩锁，避免从未收到正向 Status 时永久占位。
- **联机加入自诊断（诊断专用）**：`__TickJoinWatchdog` 在 bot 已连接但卡在 `PendingInvite/Matching/InSquad` 超 `JoinStallWatchdogSeconds`(12s) 时，一次性 `LogJoinStall` 快照（state/pendingInvite/flags/channel/remote*/inboundDrops/eventDrops），把偶发"邀请后没反应"变成确定性诊断行；不进每帧热路径、不改语义。队列溢出丢弃在 `BotRelayInboundProbe.InboundDrops/EventDrops` 计数。

**禁止**：

- bot 连接保留 `ReliableSequenced`/为消 -5 而多线程或裸猜 offset。
- 只把 Join 迁到 inject 而 Leave 仍仅走 wire（bot 不离队）。
- 移除 `CreateServerMatchingPipeline` 导致 listen driver 管线数与 server 不符。
- 收到单个 `Disconnect` 就立即转 `Leaving`，或反过来无限保留离线成员。正确边界是：保留 stage Status、立即暂停流式、统一离线宽限内允许重连，超时才退队。

### 5.6 Editor 关卡录制 / Replay 时序（不可偏离）

**原则**：`Terminator.MultiplayerBot.Recording` 与 Server 热路径一样，**帧内同步逻辑走 ECS System**，**禁止**在 `MonoBehaviour.Update` / `LateUpdate` 里轮询 sendBuffer、注入 replay、或「每帧过度防御」补状态。

| 职责 | System | Group / 顺序 |
|------|--------|----------------|
| Coop mock 激活、Login 期 Remote `Waiting→Joined` | `LevelRecordingCoopMockSystem` | `InitializationSystemGroup` |
| Remote spawn 前 property / Joined 门闩 | `LevelRecordingSpawnGuardSystem` | `InitializationSystemGroup`，`UpdateBefore(LevelPlayerSystem)` |
| sendBuffer 快照（录制） | `LevelRecordingHarnessWireSystem` | `PresentationSystemGroup`，`UpdateAfter(NetworkClientSystem)`，`UpdateBefore(ReplyMessageSystem)` |
| channelFlag 对齐、replay 注入、`BeginWhenLevelReady` | 同上 | 同上 |

**数据路径（与 ZG 包一致）**：

- **录制**：`ClientData.__Send` → `sendBuffer.EndWrite` → `LevelRecordingHarnessWireSystem` 内 `NetworkSendBufferCapture`（含 Login `ApplyStage` 的 `PlayerProperty`）。
- **回放**：录制帧 → `NetworkClientReplayInjector.TryEnqueueSyntheticData` → 下一 tick `ReplyMessageSystem` Collect（须在 `NetworkClientSystem` PopEvents **之后**注入）。

**Harness MonoBehaviour（`RecordingCoopHarness` / `ReplyMessageRecorder`）仅允许**：

- Editor 菜单 / Window 触发的 **一次性**生命周期（`PrepareAndLoadLoginScene`、`BeginRecording`、`EndRecording`、`DisableHarness`）。
- 持有 session 与配置；**不得**承载每帧 Tick。

**禁止（R1）**：

| 禁止项 | 错误形态 | 正确做法 |
|--------|----------|----------|
| Update/LateUpdate 捕获 sendBuffer | `ReplyMessageRecorder` 在 MB 帧循环里 `CaptureEndOfFrame` | `LevelRecordingHarnessWireSystem` 单点捕获 |
| Update/LateUpdate replay 门闩 | `LevelRecordingReplayPlayer.LateUpdate` 等 `IsLevelReady` | `LevelRecordingHarnessWireSystem` → `TryBeginWhenLevelReady` |
| 双路径 capture（Update + LateUpdate） | Login 与 InLevel 各写一套轮询 | 仅 WireSystem 一处 |
| 每帧 warn 刷屏 / idle 诊断 | `__LogLevelWaitIfDue` 等 2s 轮询 | 状态转换时一次性 `[RecordingDiag]` / `[BotReplay]` |
| EndRecording 造假 PlayerProperty 帧 | SharedStatic 兜底写入 `.bin` | 根因修复 + `ReportMissingPlayerProperty` 诊断 |

**程序集**：`Terminator.MultiplayerBot.Recording`（`UNITY_EDITOR`）；Filter 用 **`LocalSimulation`**（Play Mode 游戏世界），**禁止** `[WorldSystemFilterFlags.Editor]`（仅 Edit Mode 世界，Play 下不跑）。

## 6. 验收标准（共部署 Server.unity）

1. `Connect {botUserId}` — Server Accept 成功  
2. `[BotAgent] Sent MatchToSend` — Status / MatchToSend 的 inject 已被 Server Handler 消费，且 bot 进入对应 `Matching` / Server 状态；不以 outbound UTP wire 日志判定
3. **35s 内无 `Disconnect {botUserId}`**（`DisconnectReason: 1` = UTP Timeout）  
4. 日志/架构：**无** Bot 侧 per-frame `NetworkDriver.ScheduleUpdate`（Listen 除外，且 Listen 仅 Server System 驱动）  
5. **仅 1 个** `AddDriver` 的 Bot Listen Driver  
6. Init 日志 `[BotRelay] WireCatalog ready` 至少确认 Connect 模板、hello 与 link ACK 的初始化；非 Connect outbound 模板即使存在，也不得作为 Phase 3 功能前提
7. Phase 3 / Replay 验收以 inject queue drain、Server Handler 结果和 Bot Inbox 下行 ack 为准；不要求或断言 `flushed Join/ApplyMatch/Leave wire`

### 6.1 PlayMode 验收（模拟真人操作，交付门禁）

**EditMode `Regression` 是快速原理回归；凡模拟真人 / Server 热路径（`World.Update` → `NetworkRelayServerSystem` / PopEvents）的操作，以 PlayMode 自验证跑通为交付门禁，通过后再请人工 Play。**

#### 架构：App 层注入（Connect 后 bot→server 不走真实 socket）

Connect 建立后，bot→server 的全部业务消息由 **App 层 inject**（`BotRelayInjectQueue` → `NetworkRelayServerInjectSingleton` → `InjectJob` → `handler.Read`）在**单 Driver**内投递，不占真实端口、不走 UTP wire。因此**验收以状态为准**（inject 队列 drain、Handler 结果、下行答复、bot 本地状态），**不**断言 UTP 字节形状，也**不**依赖 Server 的 Burst 线程 `Debug.Log`（不经 `Application.logMessageReceived`，测试作用域抓不到）。

本用例组核心目标：**真人邀请后，bot 到底有没有主动发起 Join 答复**。

#### 交付流程（Agent / 开发自验证）

1. **编译** — 无 error  
2. **EditMode `Regression`** — `BotRelayInviteRegressionTests` + `BotRelayTransportRegressionTests` 等原理回归全绿（当前 161 条）
3. **PlayMode 验收（自动化门禁）** — `category=PlayMode` 下 `BotRelayPlayModeTests.ServerScene_CoreBotGate_InSingleSession` 必须通过；它在**一次** Server Play 会话内依次完成 6 个确定性行为检查（含空闲匹配的 farm-wide 独占锁与 Bot-vs-Bot 回退、`Timeout(120000)` 内真实等待，不可跳过或缩短）。采用多 Bot Farm，但每段操作只选一台可用 Bot，且断言其余 Bot 不并发占用；无真实 socket
4. **再请人工 Play** — 仅在步骤 2–3 全绿后，请负责人在 `Server.unity` 做一次邀请/进队复核  

**禁止提前叫人**：PlayMode 未全绿、或只跑了无延迟用例、或 MCP `init_timeout` 过短导致套件未跑完时，不得请人工介入。

##### 自动化门禁用例（`category=PlayMode`，单次 Server 会话、确定性、无 socket）

Unity 2022.3 在 Editor 测试程序集内连续 `EnterPlayMode`/同步退出会残留“Server singleton 已创建但新 ECS World 尚无 `BotRelayWorldTag`”的竞态。因此下表不是 6 次独立 PlayMode 切换，而是同一个 `ServerScene_CoreBotGate_InSingleSession` 中按顺序执行的 6 个具名检查；检查之间通过生产 inject 边界复位目标 Bot。

**测试隔离时间语义**：生产状态机将 `nextIdleMatchTime=double.PositiveInfinity` 视为“启动等待初始 Status”的哨兵，并在 Status 就绪后主动改写为当前时间、立即开始匹配。测试若要冻结非目标 Bot，必须写 `double.MaxValue`；不得用 `+Infinity` 表示“永不匹配”，否则非目标 Bot 会被重新激活并争抢 farm-wide matching lease。

| 真人 / Server 操作 | PlayMode 用例 | 必须断言 |
|------------------|---------------|----------|
| Server 启动 + bot Connect | 单会话门禁：Farm Ready 步骤 | vport / farm ready |
| 空闲 bot 匹配 | 单会话门禁：`AssertExclusiveIdleMatch` | `ScheduleExclusiveIdleMatchNow` + 匹配注入 + farm-wide 独占锁；任选目标 Bot，其他 Bot 必须保持 Idle，不得并发占用 |
| App 层生产者/Flatten 调度 | 单会话门禁：Inject Queue 步骤 | Join 写入 `BotRelayInjectQueue` 后 drain 1→0；仅证明生产者与 Flatten 调度，**不**把 queue 清空伪称为 Handler 接受。Handler 的真实 Join 语义由 `ManualHost` 端到端断言服务器 channel 成员关系 |
| 邀请 bot（RouteSend invite） | 单会话门禁：PendingInvite 步骤 | `PendingInvite` + squadId |
| **邀请后 bot 发起 Join 答复** | 单会话门禁：JoinDispatched 步骤 | 邀请 → `PendingInvite` → `Mismatch→defer→Join`；断言相应 inject 被消费并获得预期状态，不绑定 wire 计数 |
| Join 后进队（模拟下行 ack） | 单会话门禁：InSquad 步骤 | 上项 + 显式 `SimulateServerJoinAckToBot` + `InSquad`（**不**证明 Server 侧外部 channel 进队） |

##### 手动用例（`category=ManualHost` + `[Explicit]`，真实 socket 全链路，不进门禁）

真实房主由 `BotRelayHostTestClient`（`ClientData` → ReplyServer，真实 socket）模拟，验证「房主建队+邀请 → bot 自动 inject Join → Server 接受 → bot 服务器侧加入 host squad channel」的完整端到端。建队所需的首个 `SquadInvite` 仅是 `ClientData` 触发 `Create` 的载体，测试必须将它定向到未注册的 sink user，避免在明确验收目标 Bot 前向全 Farm 广播。**该真实 socket 在重复 `EnterPlayMode` 下不稳定**（`ConnectionDataMap` 越界 / `DisconnectReason:3` / `Trying to read … bits from a stream` 洪流），故归入 `[Explicit]` + 独立 category，仅人工手动跑，**不作为自动化交付门禁**：

- `BotRelayPlayModeManualTests.Live117Invite_ServerAcceptsInjectedJoin_RealSocket`
- `BotRelayPlayModeManualTests.Live117Invite_ServerAcceptsJoin_BotEntersInSquad_RealSocket`
- `BotRelayInviteAfterMatchPlayModeTests.*`（boot Match 后邀请的 Mismatch→Join 服务器接受）

> **⚠️ category 命名坑**：MCP `run_tests` 的 `category_names` 过滤是**子串匹配**，`"PlayMode"` 会误选 `"PlayModeManual"`。故手动用例 category 命名为 **`ManualHost`（不含 `PlayMode` 前缀）**，避免被 `category=PlayMode` 门禁带进去。

**为何不用 Bot-as-Host 做确定性 Server 进队验收**：farm 实际只 spawn 1 个 bot（`BotRelayFarmSpawner`：`Clamp(maxBots, minBots, botProfiles.Length)`，而 `BotConfig.asset` 仅 1 个 profile），无法用第二个 bot 当房主；且不改生产配置、不反射伪造 channel 状态。Server 侧「把 bot 放进外部 squad channel」这一步由上述手动 socket 用例覆盖。

**禁止（P8）**：PlayMode 用 silent fallback 掩盖 Join 答复失败；把手动 socket 用例混入 `category=PlayMode` 门禁充数。

**实现**：`BotRelayPlayModeAcceptance` + `BotRelayPlayModeHarness` + `BotRelayPlayModeServerProbe` + `BotRelayPlayModeLogAsserts`。**程序集**：PlayMode harness / `BotRelayHostTestClient` 在 `Terminator.MultiplayerBot.Tests`，见 [发布与测试分离](./联机机器人-发布与测试分离.md)。

**MCP**：`mode=EditMode` → `category=Regression`（快速原理，当前 161 条）；`mode=EditMode` + `category=PlayMode` → 上述单会话门禁（内部 6 项检查，`EnterPlayMode` 自进 Play，`init_timeout≥120000`）。手动全链路：`mode=EditMode` + `category=ManualHost`（`[Explicit]`，须显式选 category 才会跑）。勿用 `mode=PlayMode` 过滤（Editor 程序集下 UnityTest 仍登记为 EditMode）。

## 7. 难题与合规解法

| 难题 | ❌ 偏离解法 | ✅ 合规解法 |
|------|------------|------------|
| Connect wire | 第二 driver Connect；或复用首个 Bot 的握手 wire | Init 按 Bot 身份采模板；PreTick 仅注入该 agent 的 `connectClientWireCount` 条握手线 + `EnqueueToListen(V, wire)` |
| Status / MatchToSend | mirror `BeginSend`、prepend UTP 头、猜 session offset | 使用 ZGUP app 编码 → `BotRelayInjectQueue` → Server Handler；Connect 后先 Status 再 Match |
| Server→Bot 解 UTP | mirror `PopEvent` | PostTick drain + WireCatalog inbound 解包 → app 帧进 Inbox |
| **Link 层保活 / Timeout** | 默认 client driver fallback | **Link ACK 循环**：`PumpLinkLayerAcks` 对 server→bot 非 app link 包回注 ACK 模板；Bot Listen `NetworkSettings`：`heartbeatTimeoutMS=0`、`disconnectTimeoutMS=0`（关闭无活动断连）；Init 捕获用独立 settings（heartbeat=500）尝试采 `linkAckTemplates`，为空时回退 `statusOutboundWire` |
| SquadJoin / ApplyMatch / SquadLeave | 第二 driver 或拼接 live UTP shell | 以真实 Client 的 app 编码写 inject queue；Server Handler 处理后，以正常 `RouteSend` 下行确认。遗留 outbound shell 不参与成功判定 |
| 需要对照 Phase 0 | 默认启用 client driver | 仅 `BOT_RELAY_WIRE_FALLBACK`，默认关闭 |

### 7.1 DisconnectReason: 1（Timeout）根因（已验证）

WireCatalog 路径**没有 live UTP 客户端栈**，Bot 不会自动向 Listen 回 link 层 ACK/heartbeat。仅设 `heartbeatTimeoutMS=0` **不够**——30s 断开来自 **`disconnectTimeoutMS=30000`**（无活动超时）。合规组合：

| 参数 | Bot Listen Runtime | Init 捕获（ephemeral session） |
|------|-------------------|-------------------------------|
| `heartbeatTimeoutMS` | `0`（不发心跳，靠 ACK 回注） | `500`（便于 idle pump 采 link ACK 模板） |
| `disconnectTimeoutMS` | `0`（禁用无活动断连） | `30000`（与线上一致即可） |

> `BOT_RELAY_WIRE_FALLBACK` 35s 稳定，印证问题在 link 层而非 app 协议。
