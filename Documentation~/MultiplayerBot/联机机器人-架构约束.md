## 1. 核心目标（一句话）

**Bot 与 ReplyServer 同进程共部署：仅 1 个挂入 `MultiNetworkDriver` 的 Listen Driver。Bot 仅以 UTP wire 建立 Connect / 维护必要 link 层；Connect 后的 Bot→Server 业务消息经 Server 已开放注入 API 进入同一 `NetworkRelayServerHandler.Read`，Server→Bot 仍经 `RouteSend`、UTP 结构化解包与 Inbox；Bot 侧不对任何 driver 单独 `ScheduleUpdate`。**

---

## 2. 必须满足

| # | 约束 | 说明 |
|---|------|------|
| M1 | **唯一热路径 driver** | 只有 Bot Listen Driver 经 `NetworkRelayServer.AddDriver` 挂入 Server；**仅**由 `NetworkRelayServerSystem` / `NetworkServer.Schedule` 驱动其 `ScheduleUpdate`。 |
| M2 | **Interface 伪装远端** | 每 Bot 映射为独立 `virtualPort`。仅原始 UTP Connect 握手 / link ACK 经 `EnqueueToListen(virtualPort, utpWire)` 进入 Listen；Connect 后 Bot→Server 业务协议经 `BotRelayInjectQueue` → `NetworkRelayServerInjectSingleton` → `NetworkRelayServerHandler.Read` 投递。Server→Bot 经 `RouteSend` 进入 `virtualPort` channel，PostTick `TryDequeueToBot` → `DrainInbound` → `BotRelaySlotInbox`；下行 ClientMessage / ReplyMessage 没有第二套镜像。应用层 `NetworkRelayMessageType.Connect(type=0)` 属于该下行控制面，不是 UTP 握手。 |
| M3 | **Server 零分叉** | Relay/Identity/Handler/撮合 **不为 Bot 特化**；Accept、Handler.Read、SendBuffer 与真人一致。允许修复对真人/Bot 所有连接统一生效的公共层并发、索引或所有权缺陷，但禁止按 Bot 身份分支；包级改动见 [落地方案 §4](./联机机器人-落地方案.md) 与 §5.4.1。 |
| M4 | **传输边界：Connect 用 UTP，业务用 Server 注入** | `EnqueueToListen` 只允许 Connect 捕获线和 link ACK 模板等 **确知的 UTP wire**；禁止手工 prepend、按 offset 拼 UTP，或把裸 app / `FrameForTransport` 当 wire 注入。Connect 后的 `Status`、`MatchToSend`、`Join`、`ApplyMatch`、`Mismatch`、`Leave`、`PlayerProperty` 与回放帧，必须按 ZGUP app 编码写入 `BotRelayInjectQueue`，由 `BotRelayInjectFlattenSystem` 转入 `NetworkRelayServerInjectSingleton`，再由 Server 的既有 Handler 处理。生产 Agent / Replay 系统把注入队列视为必备依赖：队列或 Server inject singleton 不存在时必须停更并暴露配置错误，**不得**静默退回业务 UTP wire。它不是改 Server 业务逻辑，也不是绕过 Handler；它是不用猜 UTP 的正式上行入口。 |
| M5 | **Tick 分工** | PreTick：仅原始 UTP Connect wire / 必要 link ACK 注入；Server System：唯一 `ScheduleUpdate` 与注入队列消费；PostTick：下行 Drain → Inbox → Agent。Agent / Replay 产生的上行业务消息写入 inject queue，下一帧 `BotRelayInjectFlattenSystem` 在 Server System 前统一投递。 |
| M6 | **每 Bot 本地状态** | 协议/业务状态在 `BotRelayFarmNative` / `BotSessionState`；不写 `ReplyMessageShared` 等 SharedStatic。 |
| M7 | **禁止 Bot vs Bot / 抢同一队** | 不改 Server 撮合；Bot 侧保持两类原子租约：**匹配槽**只覆盖一条尚未收到 `MatchToRead` 的 outstanding `MatchToSend`，限制同一时刻只有一台 Bot 留在 Server 匹配池；收到 `MatchToRead` 后立即释放，即使临时 squad 的 Join 下一 Tick 才到，其他空闲 Bot 也可开始下一次匹配，因为第一台已退出 Server 匹配池。**队伍租约按 squadID 去重**，同一外部 Invite 仅一台 Bot 接受，但不同真人 squad 可由不同空闲 Bot 并发服务，最多受 Farm Bot 数量限制。外部 Invite 包括世界 `Public` 和指定 Bot userID 的 `Private`；`Squad` channel relay 是队内流量，不能触发空闲 Bot 加队。配对后 `remoteUserID` 为 Bot 仍须 `Mismatch`/`SquadLeave`（`BotMatchGuard`）。每个 Bot 的 squad key 在该 Bot 经 `JoinFail`、显式 Server `Drop` 或 `Leave` 回到 `Idle` 时释放；同一 channel 的后续 Invite 是新事件，仍可由空闲/匹配 Bot 接受。 |
| M8 | **链路与匹配单一事实源** | 发出 Connect 只设置 `ConnectRequested` 并清除旧 hello/`Connected`；只有收到本次真实 server hello 才设置 `Connected`，业务注册与匹配只以它为链路就绪门禁。`session.matchID==0` 表示未匹配，非零值只由当前 `ClientMessageMatchToRead` 提交；不得再引入 relay-ready、initial-status-ready 或 match-paired 镜像状态。 |

## 3. 明确禁止（曾出现偏差）

以下做法视为**偏离目标**，不得作为默认方案或「临时妥协」长期保留：

| 禁止项 | 典型错误形态 | 为何偏离 |
|--------|--------------|----------|
| **P1 第二颗 live NetworkDriver** | `BotRelayWireEncoderState.driver` 每帧 `ScheduleUpdate` / `BeginSend` / `PopEvent`（mirror encoder） | 在 Interface 外又跑一套 UTP 客户端，与「单 driver」矛盾 |
| **P2 第三颗 live UTP 栈** | `BotRelayEncodeIsland` 在热路径 `BeginSend` 并注入 live bot 的 `virtualPort` | 独立 session 的 wire 与 Accept session 不一致 → Disconnect |
| **P3 Client driver 热路径** | 重新引入 client resources、Pre/Post `ScheduleUpdate` 或业务 wire fallback | 旧 fallback 已删除；重新引入即违反单 Driver 与业务注入边界 |
| **P4 Connect 双轨** | wire 模板注入 Accept + mirror `suppress Connect` 并行建 session | 两套 UTP session，出站/入站无法与 Accept 对齐 |
| **P5 Bot 特化 Server/Relay** | 为 Bot 加 Handler 分支、SharedStatic 捷径，或仅对 Bot 改撮合语义 | 违反「Server 零分叉」原则；对所有连接一致生效的公共层正确性修复不在此列 |
| **P6 按消息猜 wire/app 编解码** | 固定/候选 offset、字节扫描猜 `ReplyMessageType`、Invite shell/文本恢复、Play 通了再补 heuristic；合成 fixture 冒充 current Capture | 每种消息重复劳动；ZGUP struct 扩充即失效；见 [传输编解码约束](./联机机器人-传输编解码约束.md) |
| **P7 混淆 Live Wire 槽位** | deferred Invite 写入 `wireLiveServerHello`；Join flush 复制 Invite listen shell 作 outbound；测试只比 `joinInj` 或固定 117B | session patch 失败或真人 `ReadFixedString512` 越界；见 §5.4 |

> **允许的唯一例外（Init-only，非热路径）**：初始化阶段可用 **一次性、采完即 Dispose** 的 ephemeral listen+client 采集 **原始 UTP Connect 握手 / server hello / link ACK** 等确知 UTP 模板；**不得**在 Pre/PostTick 对这类 driver 做每帧 Schedule。Catalog 中禁止保存 Status / Match / Join / ApplyMatch / Leave 等业务 outbound 模板，也禁止以任何业务包替代 link ACK。

## 4. 正确数据路径

```
PreTick（BotRelayPreTickSystem）
  ConnectPending → EnqueueToListen(connectWire[0..connectClientWireCount))
  PumpLinkLayerAcks（仅必要 server→bot link 包 → 注入 ACK 模板回 Listen）

NetworkRelayServerSystem（唯一 driver ScheduleUpdate）
  Listen Receive → Accept → Handler.Read → SendBuffer → Listen Send
       ↓
  RouteSend → BotRelayManager（virtualPort channel）

PostTick（BotRelayPostTickSystem / Replay Jobs）
  TryDequeueToBot → 结构化 PopEvents walk → Inbox
       ↓
  BotAgentLogic / Replay → BotRelayInjectQueue

下一帧、Server System 前（BotRelayInjectFlattenSystem）
  BotRelayInjectQueue → NetworkRelayServerInjectSingleton → Handler.Read
```

**要点**：UTP 只在 **Connect / link 层和 Server→Bot 下行** 的 `BotRelayManager` / Interface 边界处理；不再为 Bot→Server 业务消息编码或猜解 UTP。
**App 层字段顺序以 ZGUP 为准**；上行用公开 Server 注入入口，下行只允许结构化 PopEvents framing walk，禁止按消息类型猜 offset — 详见 [联机机器人-传输编解码约束.md](./联机机器人-传输编解码约束.md)。

| 模块 | 职责 | 热路径 |

| `BotRelayNetworkInterface` | Listen 端 ScheduleReceive/Send，与 Manager 队列对接 | ✅ |

| `BotRelayInjectQueue` + `BotRelayInjectFlattenSystem` | Connect 后 Bot→Server 全部业务 app 编码、排队、在 Server System 前转入 `NetworkRelayServerInjectSingleton` | ✅ |

### 5.1 WireCatalog 存储（Runtime，不可偏离）

`BotRelayWireCatalogState` 是 Init-only 的可变采集态，含原始 UTP Connect 采集状态、server hello、单值 `inboundAppPayloadOffset` 与 link ACK `NativeList`；它不保存 `inboundMappings`、候选 offset 或 Invite body，具有独立所有权与 Dispose 语义，不作为运行时 ECS 热路径组件。业务模板删除后也不得借机把这组可变容器复制到每个 Bot。

**合规布局**：

| 层级 | 内容 | 说明 |
|------|------|------|
| **Init 采集态** | `BotRelayWireCatalogState` | 只含原始 UTP Connect/server hello/link ACK/当前单值入站定位及其 `NativeList`；由 Host 持有并在 Shutdown Dispose |
| **不可变热路径数据** | `BlobAssetReference<BotRelayCatalogBlob>` | Publish 时一次构建；Blob 内同样禁止业务 outbound wire |
| **ECS 句柄** | `BotRelayWireCatalogBlobRef` | World 实体只保存 Blob 引用，Pre/Post Burst Job 从该引用读取 |
| **ECS 标记** | `BotRelayWireCatalogReadyTag` | 空 tag，表示 Host 与 Blob 已 Publish；不承载模板字节 |
| **Runtime 托管** | `BotRelayWireCatalogHost` | 负责 Init state/Blob 生命周期，不在 Burst Job 中读 managed static |

**Init 路径（仅一次，非热路径）**：

1. `BotRelayWireCatalog.Capture` — ephemeral listen+client 采原始 UTP Connect 握手/server hello/link ACK，并以 live Null-pipeline 当前 Invite 的已知 app 精确测量 `inboundAppPayloadOffset`；只发布定位值、不保存 Invite body（采完 Dispose；pump 时 drain 防 `Resetting event queue`）。
2. `BotRelayWorld` — `InitContext`（堆上）持有 `NetworkDriver`，避免栈上 16KB `InvalidProgramException`；Init `AddDriver` 经 `NetworkRelayServerManager.server`（ref 写 ECS），禁止热路径 `GetComponentData<NetworkRelayServer>` 按值拷贝。
3. `BotRelayFarmSpawner` — 创建 World 实体 → `Host.Publish` 构建 Blob → 写入 `BotRelayWireCatalogBlobRef` → 挂上 `BotRelayWireCatalogReadyTag`。

**热路径读法**（当前）：

```csharp
var catalogBlob = SystemAPI.GetComponent<BotRelayWireCatalogBlobRef>(worldEntity).blob;
// Pre/Post Job 只读 catalogBlob；业务上行另写 BotRelayInjectQueue。
```

Init 侧 `ScheduleUpdate().Complete()`、`world.Update()`（AddDriver）不在热路径并行化范围内；运行时 Job 禁止读取 `BotRelayWireCatalogHost.Catalog` 或其他 managed static。

**禁止**：

- 把可变 `BotRelayWireCatalogState` 或嵌套 `NativeList` 所有权放回 ECS 热路径。
- 每 Bot 复制一份完整 catalog（模板只读共享即可）。
- 在 Blob 中重新加入 Status/Match/Join/ApplyMatch/Leave 等业务模板。

### 5.2 热路径优先级（性能 / 安全 / Dispose）

**优先级（高 → 低）**：

1. **帧性能** — Farm Tick / Replay / Wire 收发必须走 **Burst + Job 链**（`IJob` / `IJobParallelFor`）；**禁止**为 Editor 停服或 Play 退出时的 Dispose 警告，把热路径改回主线程同步循环。
2. **内存与并发安全** — 只读数据用 **`BlobAssetReference` + `[ReadOnly]`**（WireCatalog、Replay Catalog）；可写状态用 **按 agent 分区的 `NativeArray`**；Job 间共享写（如 `BotRelayManager` 队列）须 **bucket 锁** + `[NativeDisableParallelForRestriction]`，**禁止**裸并行写同一容器。
3. **Dispose / 停服** — 仅发生在 **Shutdown / ExitingPlayMode**；允许在停服路径 `JobHandle.Complete()` / `CompleteAllTrackedJobs()`，**不得在** Wire 热路径 per-frame `Complete()`。

**禁止（曾出现偏差）**：

| 禁止项 | 错误形态 | 正确做法 |
|--------|----------|----------|
| **D1 热路径牺牲 Job** | 为消除 Replay Dispose 警告，把 `ReplayTickJob` 改为主线程 `for` | 保持 Job；Catalog 改 Blob；Shutdown 时 `CompletePending` |
| **D2 热路径 Complete** | Pre/PostTick 或 Manager 访问每帧 `Complete()` | Job 链 + `ManagerAccessHandle` 串联 |
| **D3 可写 Native 进 Job 无标记** | 并行 Job 写 `NativeList` 未 `[NativeDisableParallelForRestriction]` | 见 §5.3；或保持串行 `IJob` |

**安全约定**：

- 尽量 **不用 `unsafe`**；保留场景见 `.cursor/rules/unity-project.mdc` §2。
- Job 不持有 **已 Dispose 的 `NativeArray` 所有权**；Replay / Wire 只读视图用 **Blob 句柄**（Init 构建，Runtime 只读）。
- 跨 agent 原子状态禁止放 plain `int` 字段（并行 Job 按值拷贝会失效）。匹配使用长度 1 的 `matchingSlotOwner + Interlocked`，只覆盖 outstanding `MatchToSend`：`MatchToRead` 到达即释放，不等待临时队 Join；队伍使用长度 1 的 `squadSlotLock` 保护每 Agent 的 `squadSlotSquadKeys`，以 `squadInviteID + 1` 为 key 去重。同 key 只允许一台 Bot，不同 key 可并发；各 key 持有至对应 Bot 经 `JoinFail`/`Drop`/`Leave` 转回 `Idle`。

### 5.3 Farm Tick Job 链（当前）

| 阶段 | Job | 并行 | 说明 |
|------|-----|------|------|
| PreTick | `BotRelayPreTickBurstJob` | `IJobParallelFor` | Connect 注入（**Spawn 预分配 `virtualPort`**）与必要 link ACK；不 flush 业务 outbound |
| Post Drain | `BotRelayPostDrainBurstJob` | `IJobParallelFor` | 每 agent  dequeue 自有 virtualPort；Manager bucket 锁 |
| Post Agent | `BotRelayPostAgentJob` | `IJobParallelFor` | Inbox + `BotAgentLogic`；业务消息写 `BotRelayInjectQueue`，无 Manager |
| Post Flush | `BotRelayPostFlushBurstJob` | `IJobParallelFor` | 仅 PumpLinkLayerAcks；不 flush 业务 outbound |
| 下一帧 Server 前 | `BotRelayInjectFlattenSystem` | `ISystem` | 把生产者队列搬入 `NetworkRelayServerInjectSingleton`，由既有 Handler.Read 消费 |
| Replay | `BotRelayReplayTickSystem.ReplayTickJob` | 串行 `IJob` | 读 `[ReadOnly] NativeArray<BotReplayCatalogEntry>`；Shutdown `CompletePending` |

**Replay Catalog**：Init 时 `BotReplayCatalogBuilder` 构建 **`Persistent NativeArray<BotReplayCatalogEntry>`**（每条只含从目录解析的 `userStageID`、`levelID` / `stageIndex` 或 `sceneName` + `recording` Blob）。可加载路径是 `StreamingAssets/Recordings/{userStageID}/`、`{levelID}_{stageIndex}/` 或 `{sceneName}/`；组队与匹配 lookup 都严格按该顺序，scene 键是 `Path.GetFileName(matchStart.sceneName)`。Stage、level、stage、scene 只取自真人 `LoginManager.__Start` 发出且通过当前代际门禁的 MatchStart；`ClientMessagePlay`、`ChapterStage`、remote Status 与 TRBT Header 的 ID/sceneName 均不得用于 catalog lookup 或协议注入。三种精确键都未命中时不得以同 Level 其他 stage、其他 scene 或任意录像兜底。录制序列化只接受 **TRBT v2**；`Read` / `ReadHeader` 遇到 v1 或任意非 v2 版本必须 fail-close，不迁移、不猜字段。**不可**整表迁入 `BlobArray`；Runtime Job 以 **`[ReadOnly]`** 引用该数组，Dispose 仅在 Shutdown 且 **`CompleteReplayTick` 之后**。

**virtualPort 预分配**：`BotRelayFarmSpawner` 在首帧 Tick 前调用 `BotRelaySlotOps.AssignVirtualPortsAtSpawn`（主线程、`AllocateVirtualPortBurst`）；PreTick Job **不得**再写 port map。`TryDisconnect` 保留 `virtualPort`（Farm 生命周期内 channel 稳定）。

### 5.4 Connect / hello / link ACK 状态不变量（不可偏离）

`serverHello` 只承载 Connect 后的 server hello，用于 Connect / link 层状态对齐；任何含 Invite、Match、Join 等 app payload 的下行大包都不得覆盖它。Server→Bot 的 Invite/Match 等当前消息只经结构化 PopEvents walk 定位并交给 Inbox，不在 Catalog 中保留专用业务 shell。

**链路就绪唯一事实源（2026-07-31）**：`__RequestConnect` 注入 Connect 后只设置 `ConnectRequested`，并清除 `Connected` 与旧 `wireLiveServerHello`；不得复制 Capture 会话的 hello 冒充本次响应。`__StoreLiveHello` 收到当前连接真实 server hello 后才保存它并设置 `Connected`。业务层初始 Status、注册和空闲匹配都直接以 `Connected` 为门禁；`relayServerStatusInjected` 只记录一次真实 Status(0) 业务注入，不是第二份链路就绪状态。禁止恢复 `relayLinkReady`、`sentInitialStatus` 或空包“连接成功”事件。

**当前实现（2026-07-31）**：Status、MatchToSend、Join、ApplyMatch、Mismatch、Leave、PlayerProperty 与回放帧只走 `BotRelayInjectQueue` → `NetworkRelayServerInjectSingleton` → Server Handler。`TryEmbedLiveApp`、业务 `FlushOutbound`、Join outbound shell、业务模板槽和 client-driver fallback 均已删除；测试也必须走注入链，不能保留“无注入时改走 UTP”的兼容分支。

**Connect 身份不变量（2026-07-22）**：UTP Connect payload 含 `ClientHeader`，`virtualPort` 只区分虚拟端点，不能替代身份。初始化必须为每个 Bot 独立 Capture Connect 握手，并在 `BotRelayCatalogBlob.agentConnectClientWireRanges` 中按 agent 保存；PreTick 仅注入本 agent 的握手 wire。若复用 `profiles[0]` 的 wire，Server 会把多个 virtualPort 注册为同一 userID，后续被邀请 Bot 虽能收到下行邀请，却没有可供 Join 的 Server identity。

**应用层 Connect 不变量（当前唯一协议）**：原始 UTP Connect 握手只存在于 Transport/Catalog 路径；PopEvents 分帧后的 `NetworkRelayMessageType.Connect(type=0)` 是 Server 通知当前频道远端成员重连/在线的应用控制消息，当前结构为 `[Connect, channelFlag, userID] + EOF`。它必须经 `BotRelayWireBytes` 与 Inbox 精确解析并更新匹配 userID 的远端在线/频道快照，不能一律拒绝，不能设置 Bot 自身的 `Connected`，也不能接受截断、尾随字节或其他历史形态。

**Server Join 门禁仍有效**：`NetworkRelayServerIdentity.Join` 在 `match != 0` 时静默失败；Bot 在 Join 前必须先经注入路径投递 `Mismatch` 清除 server match。Spawn 的 `nextIdleMatchTime=∞` 表示生产不主动进池；匹配池观察经通用 `NetworkRelayServer.AsReadOnly()`（无 Bot 特化、热路径不 Complete）。

**Invite/Join 活性边界（2026-07-31）**：`PendingInvite` 的租约不能依赖 Server 必定返回 `Join` 或 `JoinFailed`。Join 只发一次；一个 `JoinFailed` 已足够确认失败，不做“两次失败”计数。若 10 秒内两者都未到达，Bot 必须 `Leave → Mismatch → Status(0)` 清理、释放自己的 squad key 并回 Idle。PendingInvite 期间早到的 ordinary MatchStart(0) 当场拒绝且不保存；之后到达的 Join 只按当前状态与当前 squadID 门禁，Idle/Leaving 一律清理，另一条 PendingInvite 只接受自己的 squadID，不保存已过期 squadID 或乱序消息。

**Invite 当前协议边界（2026-07-31）**：只接受完整 app：`PackedInt Invite(104) + PackedInt relayType + PackedUInt senderID`，Flush 到字节边界后严格读取 `levelID + stage + channel + FixedString512 + 完整 FixedBytes80`，并要求恰好 EOF。sender 只要求非零，stage/channel 非负；完整 app 自带 sender/channel 是本邀请唯一权威，`channel=0` 不改写，空闲期 Create/Join 不保存为 Invite 关联缓存。Server→Bot wire 只使用 WireCatalog 本次 Capture 发布的单一 framing；布局变化即 fail-close 并重新 Capture。禁止连续位流、截断 Header、0/8 双分支、候选 offset、shell/junk/anchor、文本/ASCII、历史长度、Catalog mapping 恢复或字段重建。

**统一 MatchStart Stage 代次边界（2026-07-31）**：`LoginManager.__Start` 在本次启动进入 `Waiting` 边界、取得权威服务器 UserStage ID 后，统一且仅一次发送 `ClientMessageMatchStart(matchID,userStageID,isRestart,levelID,stage,levelName,sceneName)`。`matchID=0` 是合法普通组队值，但仅当 `Join` 已确认 current squad 且 sender 是当前 Host 时当场消费；`matchID>0` 仅当 `MatchToRead` 已建立当前匹配代次、频道关系有效且消息 matchID 与当前非零 matchID 一致时当场消费。非零 `session.matchID` 提交后具有代次不可变性：同 ID 重复通知只允许幂等，不同非零 MatchToRead 必须拒绝，不能覆盖当前描述或清空其 phase/replay。Server→Bot 的 Mismatch 通知必须完整读出 matchID，且只有等于当前非零 matchID 时才能取消该代次；旧/外来 Mismatch 必须忽略。任何早到、跨邀请、跨队、旧代次或 ID 不符的 MatchStart 都直接拒绝，禁止 pending、乱序缓存或稍后复活。

**Play / ChapterStage 隔离边界（2026-07-31）**：两者保持当前真人协议结构。Bot 下行协议层必须按完整当前结构读取并消费到 EOF，保证同一 PopEvents wire 中的后续帧仍可解析；随后不生成 Bot 状态事件。Bot 不发送 Play，也不将 Play、ChapterStage、remote Status 或其他字段拼成进关描述；普通组队和匹配均不提供旧 Bot 协议兼容分支。缺少合法 MatchStart 时必须等待或 fail-close，不能从目录名、TRBT Header、本地 `UserDataMain` 或编号规律补 Stage。

**进关资料必须 fail-closed（2026-07-31）**：通过代际门禁的 MatchStart 解析出 Stage/tuple 后，严格按 `StageID → LevelID_stage → Path.GetFileName(matchStart.sceneName)` 查找，不改变目录优先级。三类精确键均未命中、选中录像没有可用的首个 `PlayerProperty`，或首个 PlayerProperty 无法成功注入时，Bot 必须保持 `Status=0`、不得启动 replay，并输出本次 Stage/level/stage/scene 与失败原因。禁止用“只发非零 Status”、跨目录猜录像或跳过 PlayerProperty 冒充远端登录成功。

**两条匹配路径的阶段边界（2026-07-29，不可推断）**：预组队路径在撮合前会收到 `ClientMessageType.ApplyMatch`，Bot 只回同类型消息表示同意，队长随后才发 `MatchToSend`；单人撮合形成临时队伍时没有 `ApplyMatch` 阶段，直接等待撮合成功。`NetworkRelayMessageType.Create/Join` 在两条路径中都只确认频道成员关系，不能写匹配绑定。处理 Join 确认时必须由状态迁移同步提交 `session.channel`，不得只依赖 Inbox 的前置副作用；`InSquad + CHANNEL_NULL` 属非法中间态。预组队路径即使收到非零 `ChapterStage`，在 `MatchToRead` 前本地 `channelStatus` 仍必须保持 0，ApplyMatch 回复旁不得夹带 Status。唯一共同且权威的匹配成功事件是 Server 下发的 `ClientMessageMatchToRead`（relay `Match`）；只有在 `session.matchID==0` 时，该事件可以把非零 ID 写入 `session.matchID` 并进入 `Register + ApplyStart + __Start` 流程；相同 ID 重复只幂等，不同非零 ID 不得换代覆盖，迟到的 `ApplyMatch` 必须忽略。`session.matchID` 是唯一匹配绑定事实源，不存在 `matchPaired` 镜像布尔值。Match 是新的 Stage 代次边界：首次提交时清除上一代 `levelStartMessages`、登录 phase、replay 与仅供诊断的远端 Stage 快照，然后等待真人 `LoginManager.__Start` 广播同 matchID 的 MatchStart；Match 前早到的描述拒绝且不缓存。Bot 收到当前描述后分两 Tick：先仅发送录制首个 `PlayerProperty` 且保持 `Status=0`，下一 Tick 再发送 `PlayerProperty + Status(stageID)` 并启动回放。普通组队不需要 MatchToRead，但只有 Join 已确认 current squad/Host 后新到的 `MatchStart(matchID=0)` 可以授权 Bot；Play/ChapterStage 在协议层完整消费，但不能提供 Bot 进关 Stage。录像未精确命中、首个 PlayerProperty 缺失或注入失败必须 fail-closed。进关后不得追加 `Status(0)`；清零只属于真正的 Leave 或与当前代次相符的 Mismatch。

**MatchStart 显式类型优先（2026-07-30）**：Server→Bot wire 先按本次 Capture 的唯一 framing 得到完整 app；若首个 type 为 `ClientMessageMatchStart(type=24)`，必须校验完整 SendRelay envelope/body 后原样提交，`matchID=0` 必须通过 L2 完整体校验，普通组队/匹配关联留给状态层。不得做 inner-offset 猜测，`levelName/sceneName` 是任意 UTF-8 字节，扫描其内部会产生伪造的合法控制类型。该 Channel 是可靠通道，发送端保持 `LoginManager.__Start` 单次发送，不以循环重发掩盖接收端解码错误。状态层对零/非零 MatchStart 都不得缓存：门禁已成立则当场消费，否则拒绝。完整 `Play(type=21)` 与 `ChapterStage(type=20)` 仍须先按当前结构校验并整包消费，避免其内部字节被二次识别；二者都不会生成 Bot 进关事件。

**统一发送端必须 fail-close（2026-07-31）**：`LoginManager.__Start` 只有在本次权威 `userStageID` 已解析且 `IClientData.instance` 有效时，才允许发送 MatchStart 并继续远端登录握手；普通组队写 `matchID=0`，匹配写当前非零 matchID。缺任一前置条件必须记录错误后退出，禁止在“描述未发送”的情况下继续本地进关并让远端永久等待。

**Job 调用链 helper 不得生成独立 Burst 直调入口（2026-07-26）**：`BotReplayLogic.Stop/Tick` 只允许作为普通静态 helper；`Stop` 在 `BotRelayPostAgentJob → BotAgentLogic` 下由外层 Burst Job 传递编译，在 `BotRelayReplayLoadJob` 等 managed 调用方下直接执行；`Tick` 由 `ReplayTickJob` 传递编译。方法级 `[BurstCompile]` 会额外生成 `$BurstDirectCall` 包装，Linux/Mono 在 managed Job fallback 中解析该包装时会因 `$BurstManaged` 缺少 `MonoPInvokeCallback` 抛异常。尤其 `SquadJoin` 已先清除 pending invite、写入 channel，随后由 `__ClearCommittedLevelStart → Stop` 清理旧 replay；若此处抛异常会阻断最后的 `InSquad` 迁移，形成不可接受的半提交状态。门禁 `ReplayJobHelpers_DoNotExposeStandaloneBurstDirectCallEntrypoints` 必须保持全绿；Linux 发布包还须确认日志中不再出现 `Stop$BurstManaged` / `Stop$BurstDirectCall`，且一次 Join 确认后稳定进入 `InSquad`。

**测试原则**：验证 Connect 时检查 UTP template / hello 不变量；验证业务消息时检查 inject queue 被 drain、Server Handler 的结果状态和下行 ack。禁止以固定 wire 长度、`joinInj` 计数或任意 outbound UTP 字节形状作为 Join 成功证明。

### 5.4.1 Server 公共注入与连接槽不变量（不可偏离）

以下约束位于 `ZG.Entities.Networking.Common`，对真人和 Bot 一致生效；它们是公共网络层正确性修复，不是 Bot 特化分支：

| 不变量 | 正确语义 | 禁止退回的旧形态 |
|--------|----------|------------------|
| **同 userID 注入串行** | `NetworkRelayServerInjectSingleton.injects` 先按 userID 做稳定分组；不同 userID 组仍可并行，同一组只创建一次 Identity，并严格按原始 inject 顺序逐条调用 Handler | 直接按每条 inject 做 `IJobParallelForDefer`，让同一 Identity / SendBuffer 在同一 Tick 被并行写入 |
| **Disconnect 槽位同步** | `__connections.RemoveAt(index)` 是有序左移；`__sendBuffers` 与 `__targets` 必须按相同 index 同步左移。被移除槽先 `Clear`，再放到旧活动区末尾作为唯一 spare；活动连接的 pending backlog 不得丢失或串给其他 userID | 只移动 `__connections` / index map，发送槽仍停在旧位置；或在搬移时 Dispose/复制出两个嵌套 Native 容器所有者 |
| **retry Append 首条不丢** | `Append(source, index)` 的 `index` 是**第一条未发送消息**；源字节起点为 `index == 0 ? 0 : source.sizes[index - 1]`，所有累计 endpoint 按目标当前 byte length 重基 | 从 `source.sizes[index]` 起拷，静默跳过第一条未发送消息；MatchStart、PlayerProperty、Status、Join 等关键帧可能因此永久缺失 |

同 userID 分组必须保持生产者入队顺序，不能按消息类型二次排序；Disconnect 槽位搬移必须与 `NetworkConnection` 的有序 `RemoveAt` 语义绑定，不能假定 swap-back。`NetworkSendBuffer.Append` 遇到破损累计端点时应 fail-closed，不得越界复制。

公共门禁位于 `ZG.Entities.Networking.Common.Tests`：原有 9 条覆盖交错/同 ID burst 分组、Append 的 0/中间/末尾/no-op 边界、Disconnect 首位/中间/反复重连槽位所有权；另有 EndWrite capture suite 覆盖同 slot/跨 slot 顺序、stamp、Apply/Clear 生存期、empty write、Peek/Consume、sequence wrap 与并发 producer。当前工程须在 `Packages/manifest.json:testables` 中启用 `cn.com.zerogame.unitypackages.entities.networking.common`；测试程序集只在 Editor 编译，不进入 Linux Player。

### 5.5 Server→Bot 空管线 + per-userID 路由（不可偏离）

**历史根因（`NetworkSendMessage: -5`，已验证并修复）**：Server 默认对每条连接建 `[Fragmentation, ReliableSequenced]` 管线。早期单 Driver Bot 尚未实际回注 link ACK，可靠发送窗口无法推进，最终出现 `NetworkSendQueueFull(-5)`；同时可变管线头诱发了猜 payload 起点的错误方向。当前实现会用本次真实 server hello/session patch 生成并实际回注 Capture 的 link ACK，同时 Server→Bot 业务发送仍走下述空管线；这段只解释旧故障，不表示 `Connected` 前可使用旧 hello/ACK。

**方案：bot 连接改走 UTP 空管线（no pipeline stages）**。

| 机制 | 做法 |
|------|------|
| **单一来源** | `BotRelayPipeline.Null`（= `default(NetworkPipeline)`）为所有 bot 连接唯一管线；命名/引用全岛对齐 |
| **per-userID 路由** | Spawn 后 `BotRelayFarmSpawner.__RouteBotsThroughNullPipeline` 写 `NetworkRelayServerInjectSingleton.pipelines[userID] = Null`；server 发送路径 `NetworkServerSendBuffer.Send` 解析 `pipelines.TryGetValue(userID) ? that : Pipeline`——**bot 走空管线，真人保留默认可靠+分片管线**（真人收 bot 消息不受影响） |
| **listen driver 计数不变量** | bot listen driver 挂入 server `MultiNetworkDriver` 需与 udp/ws driver **管线数一致**（否则 `AddDriver` 抛 "must have 1 pipelines, but has 0"）。`BotRelayPipeline.CreateServerMatchingPipeline` 建一条匹配的 `[Fragmentation, ReliableSequenced]` 仅满足计数/索引不变量；**bot 实际发送仍经 per-userID map 落到 `Null`** |
| **单一确定性解码** | `catalog.inboundAppPayloadOffset` 由 live Null-pipeline 当前 Invite Capture 测得并指向首个 app；Runtime 只从 `offset - sizeof(ushort)` 开始 PopEvents framing walk 并要求完整消费，Capture 后不保存 Invite body。offset 缺失/不符即 fail-close。**没有** 0/8 双分支、第二候选或逐消息启发式扫描；改管线必须重新 Capture 并重测该唯一 offset |

**为何解决 -5 与「不好维护/留后患/无法扩展」三点**：空管线消除 server→bot 的 `ReliableSequenced` 发送窗口饱和；inbound 只做确定性 framing walk，不猜消息；而 **全部** Bot→Server 业务消息均经 App 层 inject 可靠投递，不再把 session 相关 UTP 组包当作可维护方案。管线变更时只需重验 Connect / 下行 framing，不需要为每个上行协议重抓包、补 offset。

**业务上行必须走 inject（不可偏离）**：`Status`、`MatchToSend`、`Join`、`ApplyMatch`、`Mismatch`、`SquadLeave`、`PlayerProperty` 以及回放 gameplay 帧都必须经 `BotRelayInjectQueue` 投递。`BotState.Leaving` 的 `SquadLeave` + `Status(0)` 尤其不能只写 outbound wire，否则 server 不会移除 bot，表现为完成关卡或房主离线后 bot 不离队。

**注入负载上限（2026-07-22）**：queue item 直接存 `BotRelayPacket`，上限与 relay app 一致为 `1472B`，不得再用 `FixedList512Bytes` 截断或拒绝合法录制帧。经 2026-07-23 校验，资源工程 `Terminator_Resource/Assets/StreamingAssets/Recordings` 的 106 个文件均可解析；规范目录可为 `{StageID}`、`{LevelID}_{stage}` 或真实 `sceneName`（如 `Level*.scene`），三类都会进入生产 catalog。**该目录被当前源码工程的 `Assets/.gitignore` 忽略，不能把资源工程盘点误称为当前工程已部署**。旧 500B 上限会静默丢失 `511–680B` 录制帧，可能导致 `PlayerProperty` 握手或进关动作回放缺失。超过 `1472B` 的未来录制必须在录制校验阶段报错/隔离，不能在生产回放中默默跳过。

**回放格式与时间轴门禁（2026-07-31）**：部署文件只允许 `magic=TRBT, version=2`；`LevelRecordingSerializer.Read` 与 `ReadHeader` 对 v1、未知版本、截断或尾部损坏必须直接失败，不做迁移或兼容读取。v2 帧时间戳按文件顺序必须单调不减。录制端只接受 completed-`EndWrite` journal 随 payload 原子提交的 producer `epoch + double timestamp`；不得读取 transport 槽后按采样点插值、均摊或补时间。RecordingAudit 对任意倒退报 `NonMonotonicTimestamps` Error；同一 timestamp 下 Move 总数或 byte-identical Move 数 `>=8` 才报 `CollapsedMoveTimestamps` Error，2–7 条相同 payload 报 `DuplicateSameTickMove` Warning，同帧不同 payload Move 合法；相邻 Move 超过 15 秒报 `LargeMoveGap` Warning。运行时继续累加完整 Server Delta、注入全部到期帧，不以固定条数、慢放或修复器掩盖坏素材。旧异常录像必须重录。逐包 `RouteSend peeled` 仅可在 `VerboseTelemetry` 下输出；已经删除按 80–160B 长度猜测 Invite 的 `InviteShell` 遥测与测试，长度永远不是 Invite 类型判据。

**InLevel 期间真人退出 / 掉线的 -5：区分两个正交信号（不可混用）**：`channelFlag` 低位是 `NetworkRelayChannelFlag`（`Online` 在线位），`>> ShiftToStatus` 才是**关卡状态值**（stageID）。二者语义正交，`BotSessionState` 分别记录 `remoteChannelStatus`（状态值）与 `remoteOnline`（在线位）：

- **真人彻底离开关卡 / 返回大厅** → `remoteChannelStatus == 0`。这是**原设计的退队条件**（"channelStatus=0 才退队"）。`__TickChannelTracker` InLevel 分支据此（经 `InLevelReplayArmGraceSeconds` 3s + `RemoteLeaveWhileInLevelDebounceSeconds` 2s 去抖，滤掉房主每帧 Create/Join/Leave 重播抖动）转 `BotState.Leaving`。
- **房主明确移除 Bot** → Server 下发 `NetworkRelayMessageType.Drop`。它不是上述瞬时 `Leave` 重播，必须在 Agent 事件队列内立即停止回放、清空频道/Stage、回到 Idle 并释放该 Agent 的 `squadSlotSquadKeys`；同批后续 Invite 以清理后的状态重新竞争租约。
- **录像播放耗尽** → 只表示没有更多录制动作；**不得**把 `Playing` 清位当作出关，Bot 必须继续保持 `InLevel` 和队伍占用，并忽略新的世界/私有邀请，直到上述实时 `remoteChannelStatus == 0` 退队条件成立。邀请入口除检查状态外，还须以本地/远端 channel status、目标 StageID 和 replay runtime 作为状态同步延迟的守卫。
- **所有队伍统一离线宽限**：`Disconnect` 只将 `remoteOnline=false`，不得把没有携带 Status 的包误解为 `remoteChannelStatus=0`；大厅普通队、匹配临时队、关内队统一由 `BotAgentState.remoteOfflineSince` 计时。默认 `BotConfig.remoteOfflineLeaveTimeout=5s`（长于客户端 2s 自动重连等待）：宽限内重连则清零计时并保留队伍，超时则 Bot 转 `Leaving`，inject `SquadLeave + Status(0)` 释放占位。
- **匹配成功但真正进关前掉线**：同样走上述 5s 宽限，不应在通用 `NetworkRelayServerIdentity.Disconnect` 中立即 `Leave`；否则客户端只收到 `Leave` 而非可靠的匹配取消终态，可能与已启动的 Match/UI/ApplyStart 异步流程竞争。超时后由 Bot 主动离队完成清理。
- **-5 根因与统一处置**：server 对频道成员转发**不看** `isOnline`（`NetworkRelayServerIdentity.Relay(Channel)` 直写频道缓冲），因此真人退出（status 0）**或**掉线（offline）都会让 bot 的回放 gameplay 持续灌入不再 ACK 的真人可靠窗口 → `-5`。故只要真人"不在消费"（offline **或** status 0），`__TickChannelTracker` 立即置 `BotAgentRuntimeFlags.RemoteAbsentSuppressed`；`BotRelayReplayTickSystem.ReplayTickJob` 见此位**跳过 `BotReplayLogic.Tick`（暂停回放：不推进 playbackTime、不 inject）**。真人在宽限内重连即清位续播；offline 超过统一超时或 status 0 通过关卡离场去抖后，Bot 正式退队。
- **抑制必须"先确认在场"（避免进关看不到机器人）**：`remoteOnline` 默认 `false`，只在收到带 `Online` 位的 channel/status 消息时才置真。若直接以 `present==false` 抑制，进关瞬间（或该消息尚未刷新）就会误置 `RemoteAbsentSuppressed` → 回放永不推进 → **机器人隐身**。故用 `BotAgentState.remotePresenceSeen` 闩锁：仅在正向观测到 `present`（online 且 status≠0）后才允许后续缺席触发**流式抑制**；统一离线计时则以已知远端成员（`remoteUserID/remotePlayerCount`）为权威，不依赖该闩锁，避免从未收到正向 Status 时永久占位。
- **联机加入活性与自诊断**：`PendingInvite` 在 Join 发出后使用 10 秒**语义超时**主动清理/释放，不再只记录 `JOIN-STALL`。`__TickJoinWatchdog` 的 12 秒快照保留用于 `Matching/InSquad` 等异常阶段诊断（state/pendingInvite/flags/channel/remote*/inboundDrops/eventDrops），不承担释放租约的业务语义。队列溢出丢弃在 `BotRelayInboundProbe.InboundDrops/EventDrops` 计数。

**禁止**：

- bot 连接保留 `ReliableSequenced`/为消 -5 而多线程或裸猜 offset。
- 只把 Join 迁到 inject 而 Leave 仍仅走 wire（bot 不离队）。
- 移除 `CreateServerMatchingPipeline` 导致 listen driver 管线数与 server 不符。
- 收到单个 `Disconnect` 就立即转 `Leaving`，或反过来无限保留离线成员。正确边界是：保留 stage Status、立即暂停流式、统一离线宽限内允许重连，超时才退队。

### 5.6 Editor 关卡录制 / Replay 时序（不可偏离）

**原则**：`Terminator.MultiplayerBot.Recording` 与 Server 热路径一样，**帧内同步逻辑走 ECS System**，**禁止**在 `MonoBehaviour.Update` / `LateUpdate` 里轮询 sendBuffer、注入 replay、或「每帧过度防御」补状态。

| 职责 | System | Group / 顺序 |
|------|--------|----------------|
| 发布 producer `epoch + double timestamp` | `LevelRecordingCaptureClockSystem` | `InitializationSystemGroup, OrderFirst`；先完成上一 producer window，再推进 capture clock |
| Coop mock 激活、Login 期 Remote `Waiting→Joined` | `LevelRecordingCoopMockSystem` | `InitializationSystemGroup` |
| Remote spawn 前 property / Joined 门闩 | `LevelRecordingSpawnGuardSystem` | `InitializationSystemGroup`，`UpdateBefore(LevelPlayerSystem)` |
| drain EndWrite journal（录制） | `LevelRecordingCaptureSystem` + `LevelRecordingPostReplyCaptureSystem` | `PresentationSystemGroup`；分别在 `NetworkClientSystem` 前与 `ReplyMessageSystem` 后完成 producer jobs 并 drain |
| channelFlag 对齐、replay 注入、`BeginWhenLevelReady` | `LevelRecordingHarnessWireSystem` | `PresentationSystemGroup`，`UpdateAfter(NetworkClientSystem)`，`UpdateBefore(ReplyMessageSystem)` |

**数据路径（与 ZG 包一致）**：

- **录制**：`BeginEndWriteCapture` → capture clock 发布 producer `epoch + double timestamp` → `ClientData.__Send` / `ReplyMessageSystem` 正常 `sendBuffer.EndWrite` → 独立 journal 原子提交 payload/sequence/stamp → `NetworkSendBufferCapture` 依次 Peek/复制/Consume（含 Login `ApplyStage` 的真实 `PlayerProperty`）。
- **回放**：录制帧 → `NetworkClientReplayInjector.TryEnqueueSyntheticData` → 下一 tick `ReplyMessageSystem` Collect（须在 `NetworkClientSystem` PopEvents **之后**注入）。

录制 journal 与 transport send/retry cursor 完全独立：`Apply`、`Clear`、发送成功/失败都不能消费或重置 journal，录制也不能推进 transport 游标。捕获点放在 Network/Reply 系统两侧是 producer 同步边界，不是为了在 `Apply/Clear` 前抢读槽位。录制启动、stamp 推进、Peek/Consume、clean end 任一失败都必须记录 `captureError` 并阻止保存。

**Harness MonoBehaviour（`RecordingCoopHarness` / `ReplyMessageRecorder`）仅允许**：

- Editor 菜单 / Window 触发的 **一次性**生命周期（`PrepareAndLoadLoginScene`、`BeginRecording`、`EndRecording`、`DisableHarness`）。
- 持有 session 与配置；**不得**承载每帧 Tick。

**禁止（R1）**：

| 禁止项 | 错误形态 | 正确做法 |
|--------|----------|----------|
| Update/LateUpdate 捕获 sendBuffer | `ReplyMessageRecorder` 在 MB 帧循环里 `CaptureEndOfFrame` | `LevelRecordingHarnessWireSystem` 单点捕获 |
| Update/LateUpdate replay 门闩 | `LevelRecordingReplayPlayer.LateUpdate` 等 `IsLevelReady` | `LevelRecordingHarnessWireSystem` → `TryBeginWhenLevelReady` |
| transport 槽扫描/外部游标 | `TryReadPendingSend*` + per-slot cursor，依赖 Apply/Clear 的 index 生命周期 | 只消费独立 completed-EndWrite journal |
| 批次时间插值/补时间 | 把一个采样点的积压帧均摊到前后时间，或写到未来采样点 | 保存各 EndWrite 提交时的 producer stamp；不修改 |
| 双路径 capture（Update + LateUpdate） | Login 与 InLevel 各写一套轮询 | 统一 journal；ECS 系统只负责 producer 边界与 drain |
| 每帧 warn 刷屏 / idle 诊断 | `__LogLevelWaitIfDue` 等 2s 轮询 | 状态转换时一次性 `[RecordingDiag]` / `[BotReplay]` |
| EndRecording 造假 PlayerProperty 帧 | SharedStatic/本地属性/fixture 兜底写入 `.bin` | 只接受 journal 中真实 EndWrite；缺失则诊断 + 保存硬失败 |

**保存硬门禁**：`LevelRecordingEditorWindow` 在弹出保存路径和写文件之前，必须以 `LevelRecordingFileValidator.ValidateSession` 校验内存 Session；任一 Error 都不写文件。`LevelRecordingSerializer.Write` 还必须在创建/截断目标文件之前做结构预检。禁止保存后再靠回放端插值、丢帧、补写 PlayerProperty 或其他合成修复。

**程序集**：`Terminator.MultiplayerBot.Recording`（`UNITY_EDITOR`）；Filter 用 **`LocalSimulation`**（Play Mode 游戏世界），**禁止** `[WorldSystemFilterFlags.Editor]`（仅 Edit Mode 世界，Play 下不跑）。

## 6. 验收标准（共部署 Server.unity）

1. `Connect {botUserId}` — Server Accept 成功  
2. `[BotAgent] Sent MatchToSend` — Status / MatchToSend 的 inject 已被 Server Handler 消费，且 bot 进入对应 `Matching` / Server 状态；不以 outbound UTP wire 日志判定
3. **35s 内无 `Disconnect {botUserId}`**（`DisconnectReason: 1` = UTP Timeout）  
4. 日志/架构：**无** Bot 侧 per-frame `NetworkDriver.ScheduleUpdate`（Listen 除外，且 Listen 仅 Server System 驱动）  
5. **仅 1 个** `AddDriver` 的 Bot Listen Driver  
6. Init 日志 `[BotRelay] WireCatalog ready` 只确认原始 UTP Connect 握手、server hello、link ACK 与当前 `inboundAppPayloadOffset` 初始化；该 offset 来自 live Null-pipeline 当前 Invite Capture，但 Catalog 不保存 Invite body，且不得出现任何业务 outbound 模板
7. Phase 3 / Replay 验收以 inject queue drain、Server Handler 结果和 Bot Inbox 下行 ack 为准；不要求或断言 `flushed Join/ApplyMatch/Leave wire`

### 6.1 PlayMode 验收（模拟真人操作，交付门禁）

**EditMode `Regression` 是快速原理回归；凡模拟真人 / Server 热路径（`World.Update` → `NetworkRelayServerSystem` / PopEvents）的操作，以 PlayMode 自验证跑通为交付门禁，通过后再请人工 Play。**

#### 架构：App 层注入（Connect 后 bot→server 不走真实 socket）

Connect 建立后，bot→server 的全部业务消息由 **App 层 inject**（`BotRelayInjectQueue` → `NetworkRelayServerInjectSingleton` → `InjectJob` → `handler.Read`）在**单 Driver**内投递，不占真实端口、不走 UTP wire。因此**验收以状态为准**（inject 队列 drain、Handler 结果、下行答复、bot 本地状态），**不**断言 UTP 字节形状，也**不**依赖 Server 的 Burst 线程 `Debug.Log`（不经 `Application.logMessageReceived`，测试作用域抓不到）。

本用例组核心目标：**真人邀请后，bot 到底有没有主动发起 Join 答复**。

#### 交付流程（Agent / 开发自验证）

1. **编译** — 无 error  
2. **公共网络层回归** — `ZG.Entities.Networking.Common.Tests` 全绿（必须包含 EndWrite capture suite；以 Unity 本次实际发现数为准）
3. **EditMode `Regression`** — `Terminator.MultiplayerBot.Tests` + `Terminator.MultiplayerBot.Recording.Tests` 原理回归全绿（当前合计 175 条）
4. **PlayMode 验收（自动化门禁）** — `category=PlayMode` 下 `BotRelayPlayModeTests.ServerScene_CoreBotGate_InSingleSession` 必须通过；它在**一次** Server Play 会话内依次完成确定性行为检查（含 outstanding MatchToSend 的 farm-wide 独占、MatchToRead 即时释放与 Bot-vs-Bot 回退，`Timeout(120000)` 内真实等待，不可跳过或缩短）。采用多 Bot Farm，但每段操作只选一台可用 Bot；无真实 socket
5. **再请人工 Play** — 仅在步骤 2–4 全绿后，请负责人在 `Server.unity` 做一次邀请/进队复核

**禁止提前叫人**：PlayMode 未全绿、或只跑了无延迟用例、或 MCP `init_timeout` 过短导致套件未跑完时，不得请人工介入。

##### 自动化门禁用例（`category=PlayMode`，单次 Server 会话、确定性、无 socket）

Unity 2022.3 在 Editor 测试程序集内连续 `EnterPlayMode`/同步退出会残留“Server singleton 已创建但新 ECS World 尚无 `BotRelayWorldTag`”的竞态。因此下表不是 6 次独立 PlayMode 切换，而是同一个 `ServerScene_CoreBotGate_InSingleSession` 中按顺序执行的 6 个具名检查；检查之间通过生产 inject 边界复位目标 Bot。

**测试隔离时间语义**：生产状态机将 `nextIdleMatchTime=double.PositiveInfinity` 视为「不主动 MatchToSend」（reactive：`NetworkRelayServer.AsReadOnly().matchIDs` + `matchTimeout*` 派遣）。测试/harness 若要强制某 Bot 发 MatchToSend，写有限值（如 `0`）；冻结非目标 Bot 写 `double.MaxValue`（有限且远期），避免与目标 force 竞态。

## 7. 难题与合规解法

| 难题 | ❌ 偏离解法 | ✅ 合规解法 |
|------|------------|------------|
| Connect wire | 第二 driver Connect；或复用首个 Bot 的握手 wire | Init 按 Bot 身份采模板；PreTick 仅注入该 agent 的 `connectClientWireCount` 条握手线 + `EnqueueToListen(V, wire)` |
| Status / MatchToSend | mirror `BeginSend`、prepend UTP 头、猜 session offset | 使用 ZGUP app 编码 → `BotRelayInjectQueue` → Server Handler；Connect 后先 Status 再 Match |
| Server→Bot 解 UTP | mirror `PopEvent` | PostTick drain + WireCatalog inbound 解包 → app 帧进 Inbox |
| **Link 层保活 / Timeout** | client driver 或用业务包冒充 ACK | **Link ACK 循环**：只回注 Init 捕获的 link ACK 模板；Bot Listen `NetworkSettings`：`heartbeatTimeoutMS=0`、`disconnectTimeoutMS=0`（关闭无活动断连）。捕获不到 ACK 时 fail-close 并报错，不回退到 Status 或其他业务 wire |
| SquadJoin / ApplyMatch / SquadLeave | 第二 driver 或拼接 live UTP shell | 以真实 Client 的 app 编码写 inject queue；Server Handler 处理后，以正常 `RouteSend` 下行确认。Catalog 不保留业务 outbound shell |
| 诊断/测试 | 恢复旧 client-driver 或业务 wire fallback | 禁止；测试与生产共用 Server 注入边界 |

### 7.1 DisconnectReason: 1（Timeout）根因（已验证）

WireCatalog 路径**没有 live UTP 客户端栈**，Bot 不会自动向 Listen 回 link 层 ACK/heartbeat。仅设 `heartbeatTimeoutMS=0` **不够**——30s 断开来自 **`disconnectTimeoutMS=30000`**（无活动超时）。合规组合：

| 参数 | Bot Listen Runtime | Init 捕获（ephemeral session） |
|------|-------------------|-------------------------------|
| `heartbeatTimeoutMS` | `0`（不发心跳，靠 ACK 回注） | `500`（便于 idle pump 采 link ACK 模板） |
| `disconnectTimeoutMS` | `0`（禁用无活动断连） | `30000`（与线上一致即可） |

> **历史证据（已下线）**：早期 client-driver fallback 的 35s 稳定样本曾用于定位 timeout 在 link 层而非 app 协议。该路径现已删除，只能作为历史归因，不能作为运行、诊断或兼容方案。
