## 1. 为何「每种消息猜一次」不可接受



`BotRelayNetworkInterface` **不定义**应用层协议；它只把 Listen 上已编好的 UTP **wire** 经 `RouteSend` 投递到 Bot 的 `virtualPort`。  

若在 Terminator 侧用 **固定 offset、按 Invite 扫字节、Play 通了再补规则** 的方式解析各消息：



| 后果 | 说明 |

|------|------|

| **不可维护** | 每种消息一套 heuristic，无统一 mental model |

| **ZGUP 扩充即重做** | Huffman 布局变化后 offset/扫描失效 |

| **测试假绿** | 合成 wire 通过、Play 原始 hex 仍失败 |

| **与架构冲突** | 猜字节等于第二条私有协议 |



**结论**：禁止按消息类型或候选 offset 做字节 scan；只允许当前协议规定的精确 framing（见 §4、§5.C）。

## 2. 四层模型（职责不重叠）



```

RouteSend UTP wire（本次 WireCatalog Capture 绑定的单一 framing）

    │

    ▼  L2【C】按固定 stream 起点 + PopEvents ushort 分帧 walk

    │      （与 NetworkClient.PopEvents 的 ushort framing 一致）

    │

    ▼  chunk payload（**不含** message type 在 ushort 前）

    │

    ▼  L1【B】payload 内 ReadPackedInt(type) + BotRelayMessageUtility 读写字段

    │

    ▼  BotRelaySlotInbox switch(type) → Agent 状态

```



| 层级 | 模块 | 做什么 | 不做什么 |

|------|------|--------|----------|

| **L1 App** | `BotRelayMessageUtility` + `BotRelaySlotInbox` | 字段顺序对齐 ZGUP；按 **type** 分支 | 不解析 UTP wire |

| **L2 分帧** | `BotRelayPopEventsWalkOps.TryWalkServerToBotApps` / `BotRelayWireBytes.TryAcceptCurrentInboundApp` | WireCatalog 从 live Null-pipeline 当前 Invite Capture 测得唯一 `inboundAppPayloadOffset`；从 `offset - sizeof(ushort)` 开始按 `ushort size + payload` 完整 walk，再按当前 app 结构严格验证 | Capture 后不保存 Invite body；不枚举 streamStart，不同时保留 0/8 等多套 offset，不按 Invite/Match 扫 payload |

| **L3 Transport Catalog** | `BotRelayWireCatalog` Capture | 仅原始 UTP Connect/server hello/**link ACK** 模板与当前入站定位；下行可选 **整包精确匹配**（非 type 路由） | 不保存、不重建 Status/Match/Join/ApplyMatch/Leave 等业务 outbound wire；不提供旧协议或业务 fallback |
| **L0 上行注入** | `BotRelayInjectQueue` / `BotRelayInjectOps` | 按 ZGUP app 格式编码，交由 `NetworkRelayServerInjectSingleton` 和既有 Handler 消费 | 不猜 UTP header、session 或 pipeline 字节 |

| **L4 回归** | `Terminator.MultiplayerBot.Tests` `[Category("Regression")]` | 当前应用层 Connect/Invite/ApplyMatch/Play/ChapterStage/MatchStart 与 Match/Mismatch 下行锁定 **C→B→状态门禁/无事件** 全链 | 不保留旧 Bot body、截断 Invite、偏移扫描或乱序缓存用例 |



**消息类型**在 payload **第一个 `ReadPackedInt`**，与 Client `handler.Read` / Server `NetworkServerPopEventsJob` 一致；**不是** WireCatalog 的职责。

**Connect 分层**：原始 UTP Connect 握手是 Catalog/Transport wire，不会作为完整 app 交给 L1。L2 已剥离出的 `NetworkRelayMessageType.Connect(type=0)` 是当前 Server→Bot 应用控制消息，结构固定为 `[Connect, channelFlag, userID] + EOF`，用于恢复当前远端成员在线/频道快照；必须接受并严格解析，不能把它一律拒绝，也不能据此设置 Bot 自身链路 `Connected`。

**无正文频道消息**：`ApplyMatch` / `ApplyMatchFail` / `RejectMatch` / `Cancel` / `Error` 的 Client→Server 结构只有 `[type, NetworkRelayType.Channel]`，Server 转发后只有 `[type, Channel, senderID] + EOF`。C# 空 unmanaged struct 的 `UnsafeUtility.SizeOf<T>() == 1` 只是本地存储细节，绝不能把这一字节当成协议正文；`ClientMessageRelayWire` 必须在发送边界剥离它。Bot 继续按 EOF 严格校验，不保留“允许一个尾随零字节”的旧错误兼容。

## 3. 明确禁止



| ID | 禁止项 |

|----|--------|

| **C1** | 按消息类型固定 byte offset（如「Invite 从 wire offset 32 开始」） |

| **C2** | 在全 wire 上滑动找 `ReplyMessageType.Invite(104)` |

| **C3** | `__TryExtractInviteInsideFrame` / delta scan 等 **Invite 特化** 作为默认 inbound 路径 |

| **C4** | EditMode 合成 app body 冒充 Play `RouteWirePreview` hex 并通过 Regression |

| **C5** | 截断帧上无条件 `new FixedBytes80(ref reader)` |

| **C6** | ZGUP 增字段时在 `BotRelayWireBytes` 再加一段 per-type scan |

| **C7** | 为 pipeline 枚举一段 streamStart、按评分选候选，或从 junk/文本/ASCII/历史 offset 恢复 Invite |

| **C8** | 接受 Invite 的连续 packed 变体、缺失/截断 `FixedBytes80`，或把合法 `channel=0` 改写为 1 |

**唯一允许的 framing**：

- WireCatalog 在 ephemeral Bot 会话中发送当前完整 Invite，经 live Null pipeline 捕获下行，只用已知 app 精确测得一个 `inboundAppPayloadOffset`；该值指向首个 app 字节，Catalog 不保存 Invite body 或专用 shell。
- Runtime 唯一 stream 起点是 `inboundAppPayloadOffset - sizeof(ushort)`；先在该位置读小端 `ushort length`，app 从 `inboundAppPayloadOffset` 开始，再按 `ushort length + exact payload` 循环并完整消费。任意长度、EOF 或 app 结构不符即拒绝，不尝试其他起点。
- 不内置 `0/8` 双分支，不接受历史 offset。
- Transport/pipeline 变化时重新 Capture、更新同一来源并重跑回归；Capture 缺失或新 wire 不匹配即 fail-close。
- Invite app 还必须按 §5.B 的现行完整布局精确解析；它不能靠通用“合法 type”判定获得放宽。

## 4. 合规数据路径



### Inbound（Server → Bot）



1. `TryDequeueToBot` → UTP wire  

2. `BotRelayPopEventsWalkOps.TryWalkServerToBotApps`（C）只以 `inboundAppPayloadOffset - sizeof(ushort)` 计算当前 wire 的唯一 stream 起点，按 `ushort size + payload` 完整 walk，并要求精确消费。

3. Capture 只用当前完整 Invite 的已知 app 精确测量/校验 `inboundAppPayloadOffset`；Publish 后 Runtime 只持有该单值，不保存 Invite body、候选 mapping 或历史 offset，也不得把 Capture 结果当作字段恢复来源或 MatchStart 乱序缓存。

4. `BotRelayWireBytes.TryAcceptCurrentInboundApp` 与 `BotRelaySlotInbox.ParseDataPayload`：仅验证/解析已由上述 framing 分出的完整 app，**不再** scan raw wire。对“已剥离完整 app”的直接严格校验入口只是层间交接/单测入口，不是第二套 wire 解码或 fallback。



### Outbound（Bot → Server）



1. **Connect / 必要 link ACK**：仅对 Capture 得到的确知 UTP template 使用 `EnqueueToListen(virtualPort, utpWire)`。Connect wire 的 payload 带有 `ClientHeader`，因此必须按 Bot 身份分别 Capture 并在 Blob 中按 agent 取用；严禁复用首个 Bot 的握手 wire，否则多个 virtualPort 会在 Server 侧登记为同一个 userID。

2. **Connect 后全部业务协议**：Agent / Replay → `BotRelayMessageUtility` / Codec 写 app → `BotRelayInjectQueue`。

3. `BotRelayInjectFlattenSystem` 在 Server System 前转入 `NetworkRelayServerInjectSingleton` → 既有 `handler.Read`。

4. 业务成功以 Handler 结果和正常 `RouteSend` 下行确认；不得以 UTP 壳、wire 长度或拼接 offset 判断。

## 5. 方案落地评估（2026-06-28）



### B — `BotRelayMessageUtility` ✅ 已落地



- Bot 程序集内薄封装；字段顺序抄 ZGUP。

- ZGUP struct 变更 → 只改 Utility + 一条 Regression。

**当前 Invite 唯一布局**：

1. 连续读取 `PackedInt ReplyMessageType.Invite(104)`、`PackedInt relayType`、`PackedUInt senderID`；
2. 按 Server `SendRelay` 语义执行 `Flush`，从下一字节边界读取 body；
3. 依次读取 `PackedUInt levelID`、`PackedInt stage`、`PackedInt channel`、`FixedString512 text`、完整 `FixedBytes80 header`；
4. `senderID != 0`、`stage >= 0`、`channel >= 0`，并且 Header 后必须恰好 EOF；
5. 完整 app 自带的 `senderID` 与 `channel` 就是本次 Invite 的唯一权威；不得预存或回查 Create/Join 做关联门禁。`channel=0` 是合法值，不得改写。

任一步失败都拒绝整条 Invite。没有 continuous-packed、截断 Header、103/104/117B 样本、junk/anchor、文本/ASCII、固定 offset 或 Catalog mapping 恢复分支。



### C — PopEvents  transport 分帧 ✅ 可完全落地（非猜）



**权威参照**（ZGUP 包，与 Bot 应对齐）：



```csharp

// NetworkClient.PopEvents / NetworkServerPopEventsJob — Data 事件

message.size = stream.ReadUShort();

stream.ReadBytes(payload, message.size);

// handler.Read(payload) — 内部再 ReadPackedInt(type)

```



Bot 对称实现：`BotRelayPopEventsWalkOps` 结构化 walk 后交给 `BotRelaySlotInbox`。旧 managed `BotRelayConnection/BotRelayInbox/BotRelayMessageParser` 已删除，不保留双接收栈。



**当前 RouteSend wire 与 PopEvents 的差异**：



| 项 | Client/Server | Bot RouteSend |

|----|---------------|---------------|

| 输入 | Driver **已解 pipeline** 的 stream | **未解 pipeline** 的 UTP wire |

| 前缀 | 无（或已在 driver 内处理） | 由本次 WireCatalog Capture 测得并绑定，Runtime 不枚举替代值 |

| 分帧规则 | `ushort + payload` 循环 | **相同**；stream 起点在 envelope 之后 |



**合规 C 算法（`BotRelayPopEventsWalkOps.TryWalkServerToBotApps`）**：



1. WireCatalog 以 live Null-pipeline 当前 Invite Capture 测得唯一 `inboundAppPayloadOffset`；它指向首个 app 字节，Capture 后不保留 Invite body。
2. 计算唯一 `streamStart = inboundAppPayloadOffset - sizeof(ushort)`；offset 不存在、越界或与当前 wire 不符时 fail-close，不得改试 0、8 或邻近位置。
3. 从 `streamStart` 严格循环：`size = ReadUShort()`，再从紧随其后的 app 起点精确读取 `size` 字节；长度越界、尾部残留或未完整消费均使整条候选失败，不返回 partial app。
4. 每个 payload 的首个 `ReadPackedInt` 必须为当前合法 Relay/Reply type，并按该 type 的当前唯一结构精确消费到 EOF：应用层 Connect 为 `[Connect, channelFlag, userID]`；Play/ChapterStage 完整读取后不生成 Bot 状态事件；MatchStart 完整读取后进入当前代次门禁；Invite 按 §5.B 的唯一完整布局校验。
5. **禁止**候选起点评分、inner-offset、Invite delta scan、shell/anchor 或任何历史样本恢复。

`Query` 查询频道成员时，Server `SendHeader(Query)` 会在 **Query app 内**追加被查询成员的 Connect payload（`ClientHeader`）；它不是另一条独立 type=0 app。长度区间不构成消息类型；必须由上述固定 framing 取出首个 packed type 并按 Query 当前结构消费。结构化解析出的 `Query`（type 13）只更新当前频道/在线信息与诊断；不能解除进关门禁、提供 Stage/tuple 或替代 MatchStart。



**不是猜**：规则来自当前 ZGUP PopEvents 与 Bot null-pipeline RouteSend 形态；协议变化时应更新唯一 framing 并重新录制回归证据，而不是扩大扫描窗口。



### A — WireCatalog ✅ 可落地；职责收窄



| Catalog 能力 | 是否必需 | 说明 |

|--------------|----------|------|

| **原始 UTP Connect wire 序列** | ✅ | 握手注入；无 app 语义，不等于应用层 `Connect(type=0)` |

| **业务 outbound 模板**（Status/Match/Join/ApplyMatch/Leave 等） | ❌ 已删除 | Catalog 禁止保存；业务唯一走 Server inject API |

| **linkAckTemplates** | ✅ | 无 live client 时回注 link 层 |

| **serverHello / 当前入站定位** | ✅ | live Null-pipeline 当前 Invite Capture 只测量 `inboundAppPayloadOffset`，Publish 后不保存 Invite body；其余只处理当前 Connect/link 与 Server→Bot framing |

| **inboundMappings / offset 恢复 Invite** | ❌ | Invite 只由固定 framing + 当前完整结构识别 |

| **枚举 inboundAppPayloadOffset** | ❌ | runtime 只接受本次 Capture 发布的唯一 offset |



**维护**：Connect / link 变更 → 重跑 Capture；Bot→Server 业务变更 → 对齐 ZGUP app writer 与 Handler 测试；Inbound Relay 消息变更 → 改 Utility + Regression hex，**不必** per-message inbound mapping。

**PackedInt 位边界（不可用剩余字节数代替）**：`DataStreamWriter.WritePackedInt` 使用 Huffman 位打包，连续字段不保证按字节对齐。线上首个匹配通知 `[Match=11, matchID=1, level=0]` 总长只有 **2 字节 / 14 bit**，但 `ReadPackedInt` 仍可依次读出三个字段。解析已由消息结构确定的 packed 字段时，应按 ZGUP 的字段顺序直接读取，并以 `DataStreamReader.HasFailedReads` 判断截断；禁止用 `Length - GetBytesRead() >= 字段数` 之类的字节数预判。回归必须覆盖 `matchID=1, level=0, app.length=2`。

**匹配代次边界**：Server→Bot 的 `MatchToRead` / `Mismatch` 必须完整读取其 matchID 并恰好消费当前结构。`session.matchID==0` 时可由首条合法非零 MatchToRead 提交当前代次；相同 ID 重复只允许幂等，不同非零 ID 必须拒绝，不能覆盖当前描述或清空 phase/replay。下行 Mismatch 只有携带等于当前非零 `session.matchID` 的 ID 时才能取消；旧代次、外来代次或结构不完整的 Mismatch 一律忽略。这不改变 Bot 在尚未收到 MatchToRead 时通过上行 Mismatch 取消 Server outstanding match、再响应邀请的既有流程。



### D — Regression ✅ 可落地



| 用例类型 | Fixture | 断言 |

|----------|---------|------|

| **结构（C）** | 与本次 live Null-pipeline Invite Capture 绑定的当前 wire | 断言 `streamStart = inboundAppPayloadOffset - sizeof(ushort)`，精确提取全部 PopEvents app 并完整消费；拒绝替代 offset/尾部残留 |

| **App（B）** | 当前捕获 wire 提取出的 app | Utility/Inbox 只按当前 ZGUP 字段结构解析 |

| **E2E** | 当前完整 Invite app，经本次 Capture 的唯一 framing 封装 | `DrainInbound` → `PendingInvite`；截断/连续/junk/偏移变体全部拒绝 |

| **禁止** | 仅 synthetic 通过而当前捕获结构未测；为旧 Bot 格式增加兼容分支 | — |

## 7. 测试要求



见 [联机机器人.md §EditMode 自测](./联机机器人.md#editmode-自测邀请链路)。

**Connect / 下行 Wire 不变量（§5.4，原理写法）**：

| 断言 | 依据 |
|------|------|
| Catalog 的 server hello 与 Capture 结果一致 | 原始 UTP Connect / hello 槽未被业务下行污染 |
| 应用层 Connect 恢复当前远端在线/频道快照 | `[Connect, channelFlag, userID] + EOF` 精确解析；截断/尾随字节拒绝，且不设置 Bot 自身 `Connected` |
| 当前 Invite wire 可由唯一 framing + 完整 Invite reader 解析 | `inboundAppPayloadOffset` 来自 live Null-pipeline 当前 Invite Capture，且从 `offset - sizeof(ushort)` 完整 walk；Catalog 不保存 Invite body/shell，也不恢复旧字段 |
| 预组队 ApplyMatch 可形成唯一同意回复 | 真人发送端不复制空 struct 的 1B 存储；Server SendRelay 增加 senderID 后以 EOF 结束；Bot 完整解析并只在 `InSquad + matchID=0` 回复 |
| Match/下行 Mismatch 只影响当前代次 | 不同非零 Match 不覆盖已提交 ID；旧/外来下行 Mismatch 不清除当前描述 |
| 业务 inject queue drain 后取得 Handler 结果 | Connect 后上行不存在 `TryApplySessionPatch` / `FlushOutbound` fallback |
| deferred invite 仍进入 Inbox / PendingInvite | 覆盖 live boot「invite inbound not recorded」 |

具体测试名以当前 `BotRelayInviteRegressionTests` / `BotRelayTransportRegressionTests` 为准；已删除的历史 capture/compat fixture 不得写回门禁。

## 8. 历史 Invite 兼容尝试（已关闭）



早期曾为 91B/103B/104B/117B Invite 样本保留专用提取、字段差异、连续读取、截断 Header、junk/anchor 和 offset scan 方案。上述代码与测试均已删除；这些名词只用于解释历史故障，**不构成当前协议兼容要求**。当前实现只接受：

1. WireCatalog 以 live Null-pipeline 当前 Invite Capture 测得唯一 `inboundAppPayloadOffset`，并只从 `offset - sizeof(ushort)` 开始完整 PopEvents walk；
2. 当前 ZGUP 完整 Invite 字段结构，包含完整 `FixedBytes80` 且恰好 EOF；
3. 非零 sender、非负 stage/channel；完整 Invite 自带的 sender/channel 是该邀请唯一权威，不预存 Create/Join 记录做关联。

任一条件不成立即拒绝；不得降级到旧 body、其他 offset、专用 scan、字段重建或 synthetic fallback。
