## 1. 为何「每种消息猜一次」不可接受



`BotRelayNetworkInterface` **不定义**应用层协议；它只把 Listen 上已编好的 UTP **wire** 经 `RouteSend` 投递到 Bot 的 `virtualPort`。  

若在 Terminator 侧用 **固定 offset、按 Invite 扫字节、Play 通了再补规则** 的方式解析各消息：



| 后果 | 说明 |

|------|------|

| **不可维护** | 每种消息一套 heuristic，无统一 mental model |

| **ZGUP 扩充即重做** | Huffman 布局变化后 offset/扫描失效 |

| **测试假绿** | 合成 wire 通过、Play 原始 hex 仍失败 |

| **与架构冲突** | 猜字节等于第二条私有协议 |



**结论**：禁止按消息类型做字节 scan；允许 **有上界的结构规则**（见 §4、§5.C）。

## 2. 四层模型（职责不重叠）



```

RouteSend UTP wire（117B，含 pipeline 压缩前缀）

    │

    ▼  L2【C】定位 transport stream + PopEvents ushort 分帧 walk

    │      （与 NetworkClient.PopEvents / BotRelayConnection.EnqueueTransportPayload 一致）

    │

    ▼  chunk payload（如 91B；**不含** message type 在 ushort 前）

    │

    ▼  L1【B】payload 内 ReadPackedInt(type) + BotRelayMessageUtility 读写字段

    │

    ▼  BotRelaySlotInbox switch(type) → Agent 状态

```



| 层级 | 模块 | 做什么 | 不做什么 |

|------|------|--------|----------|

| **L1 App** | `BotRelayMessageUtility` + `BotRelaySlotInbox` | 字段顺序对齐 ZGUP；按 **type** 分支 | 不解析 UTP wire |

| **L2 分帧** | `BotRelayWireBytes.TryExtractAppViaTransportFraming` | `ushort size` + `size` 字节 payload；pipeline 后 **有上界** 定位 stream 起点 | 不按 Invite/Match 扫 payload 内 offset |

| **L3 Transport Catalog** | `BotRelayWireCatalog` Capture | Connect/hello/**link ACK** 模板；下行可选 **整包精确匹配**（非 type 路由） | 不重建 Status/Match/Join/Leave 等业务 UTP wire；不为 Invite/Match 做 inbound mapping 来「认消息类型」 |
| **L0 上行注入** | `BotRelayInjectQueue` / `BotRelayInjectOps` | 按 ZGUP app 格式编码，交由 `NetworkRelayServerInjectSingleton` 和既有 Handler 消费 | 不猜 UTP header、session 或 pipeline 字节 |

| **L4 回归** | `Terminator.MultiplayerBot.Tests` `[Category("Regression")]` | Play 原始 hex 锁 **C→B→Agent** 全链 | 不用合成 body 替代 live 门禁 |



**消息类型**在 payload **第一个 `ReadPackedInt`**，与 Client `handler.Read` / Server `NetworkServerPopEventsJob` 一致；**不是** WireCatalog 的职责。

## 3. 明确禁止



| ID | 禁止项 |

|----|--------|

| **C1** | 按消息类型固定 byte offset（如「Invite 从 wire offset 32 开始」） |

| **C2** | 在全 wire 上滑动找 `ReplyMessageType.Invite(104)` |

| **C3** | `__TryExtractInviteInsideFrame` / delta scan 等 **Invite 特化** 作为默认 inbound 路径 |

| **C4** | EditMode 合成 app body 冒充 Play `RouteWirePreview` hex 并通过 Regression |

| **C5** | 截断帧上无条件 `new FixedBytes80(ref reader)` |

| **C6** | ZGUP 增字段时在 `BotRelayWireBytes` 再加一段 per-type scan |



**允许（有上界、非猜 type）**：



- Pipeline wire：跳过前 **8** 字节前缀后，在 **[8, 8+24]** 内尝试 PopEvents stream 起点（与 live 117B envelope 长度同量级；见 §5.C）。

- 校验：payload 须通过 **`ReadPackedInt` + `__IsRelayAppMessageType`**，不是 Invite 专用 validator。

## 4. 合规数据路径



### Inbound（Server → Bot）



1. `TryDequeueToBot` → UTP wire  

2. **优先** `TryExtractAppViaTransportFraming`（C）  

3. 可选：`inboundMappings` **整包字节完全一致** → 缓存 app（性能/Connect，非 type 路由）  

4. `BotRelaySlotInbox.ParseTransportPayload`：仅解析 app，**不再** scan raw wire  



### Outbound（Bot → Server）



1. **Connect / 必要 link ACK**：仅对 Capture 得到的确知 UTP template 使用 `EnqueueToListen(virtualPort, utpWire)`。Connect wire 的 payload 带有 `ClientHeader`，因此必须按 Bot 身份分别 Capture 并在 Blob 中按 agent 取用；严禁复用首个 Bot 的握手 wire，否则多个 virtualPort 会在 Server 侧登记为同一个 userID。

2. **Connect 后全部业务协议**：Agent / Replay → `BotRelayMessageUtility` / Codec 写 app → `BotRelayInjectQueue`。

3. `BotRelayInjectFlattenSystem` 在 Server System 前转入 `NetworkRelayServerInjectSingleton` → 既有 `handler.Read`。

4. 业务成功以 Handler 结果和正常 `RouteSend` 下行确认；不得以 UTP 壳、wire 长度或拼接 offset 判断。

## 5. 方案落地评估（2026-06-28）



### B — `BotRelayMessageUtility` ✅ 已落地



- Bot 程序集内薄封装；字段顺序抄 ZGUP。

- ZGUP struct 变更 → 只改 Utility + 一条 Regression。



### C — PopEvents  transport 分帧 ✅ 可完全落地（非猜）



**权威参照**（ZGUP 包，与 Bot 应对齐）：



```csharp

// NetworkClient.PopEvents / NetworkServerPopEventsJob — Data 事件

message.size = stream.ReadUShort();

stream.ReadBytes(payload, message.size);

// handler.Read(payload) — 内部再 ReadPackedInt(type)

```



Bot 对称实现：`BotRelayConnection.EnqueueTransportPayload`（已存在）。



**RouteSend 117B 与 PopEvents 的差异**：



| 项 | Client/Server | Bot RouteSend |

|----|---------------|---------------|

| 输入 | Driver **已解 pipeline** 的 stream | **未解 pipeline** 的 UTP wire |

| 前缀 | 无（或已在 driver 内处理） | 通常 `byte[0]==0x01` + 8B pipeline 头 + **可变长度 envelope** |

| 分帧规则 | `ushort + payload` 循环 | **相同**；stream 起点在 envelope 之后 |



**合规 C 算法（`TryExtractAppViaTransportFraming`）**：



1. 非 pipeline wire：从 offset **0** PopEvents walk。  

2. Pipeline wire：stream 起点 ∈ **[8, 8+24]**（有上界枚举，非全包 scan）。  

3. 对每个起点：严格 PopEvents — `size = ReadUShort()`；若首帧 `size` 非法则 **此起点失败**（不 slide 逐字节）；若已经读到 app 后下一帧长度非法，该候选只算 **partial / `fullyConsumed=false`**，不得压过完整消费 wire 的候选。

4. 每个 payload：`ReadPackedInt` 须为合法 Relay/Reply type；通过则截取 **exactly `size` 字节** 为 app。  

5. **禁止** Invite 特化 delta scan 作为默认路径（旧 `TryExtractRelayAppPayload` 中部分逻辑标记淘汰）。

`Query` 查询频道成员时，Server `SendHeader(Query)` 会追加被查询成员的 Connect payload，因此 wire 可能与 Invite 同为 80–160B。长度区间不构成消息类型；必须由上述完整 PopEvents walk 取出首个 packed type。只有结构化解析出的 `Query`（type 13）可以解除 Match 后的 fresh-stage 门禁。



**不是猜**：规则来自 ZGUP PopEvents；仅 envelope 长度用 Capture/Play 确定的 **有上界**（24B），不是「找 Invite 字节码」。



### A — WireCatalog ✅ 可落地；职责收窄



| Catalog 能力 | 是否必需 | 说明 |

|--------------|----------|------|

| **Connect wire 序列** | ✅ | 握手注入；无 app 语义 |

| **历史 outbound 模板**（Status/Match/Join/Leave） | 兼容诊断 | 可用于对照、日志和迁移审计；**不是**业务投递路径，验通后列为删除候选 |

| **linkAckTemplates** | ✅ | 无 live client 时回注 link 层 |

| **serverHello / 小包整包匹配** | ✅ | 无 Relay app 或空 app |

| **inboundMappings 为 Invite 认 type** | ❌ | 由 **C + B** 替代 |

| **inboundAppPayloadOffset 作长期默认** | ❌ | 仅 Capture 辅助校验；runtime 默认走 C |



**维护**：Connect / link 变更 → 重跑 Capture；Bot→Server 业务变更 → 对齐 ZGUP app writer 与 Handler 测试；Inbound Relay 消息变更 → 改 Utility + Regression hex，**不必** per-message inbound mapping。

**PackedInt 位边界（不可用剩余字节数代替）**：`DataStreamWriter.WritePackedInt` 使用 Huffman 位打包，连续字段不保证按字节对齐。线上首个匹配通知 `[Match=11, matchID=1, level=0]` 总长只有 **2 字节 / 14 bit**，但 `ReadPackedInt` 仍可依次读出三个字段。解析已由消息结构确定的 packed 字段时，应按 ZGUP 的字段顺序直接读取，并以 `DataStreamReader.HasFailedReads` 判断截断；禁止用 `Length - GetBytesRead() >= 字段数` 之类的字节数预判。回归必须覆盖 `matchID=1, level=0, app.length=2`。



### D — Regression ✅ 可落地



| 用例类型 | Fixture | 断言 |

|----------|---------|------|

| **结构（C）** | `CapturedLiveInviteWire117Legacy` | 91B 提取于 wire[26..116]；无 stream over-read |

| **App（B）** | Legacy 提取出的 91B | Utility/Inbox 解析结果（可记录已知 ZGUP 与 live 差异） |

| **E2E** | `CapturedLiveInviteWire117`（prefix live + app 合规）或 driver-shape | `DrainInbound` → `PendingInvite` |

| **禁止** | 仅 synthetic 通过而 Legacy 结构未测 | — |
