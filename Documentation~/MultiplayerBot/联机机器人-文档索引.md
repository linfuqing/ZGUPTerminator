**Cursor 规则**：`.cursor/rules/bot-relay.mdc`（Relay 目录）、`.cursor/rules/bot-recording.mdc`（Recording 目录）、`.cursor/rules/unity-project.mdc`（Burst/热路径规范）。

**热路径原则（摘要）**：帧性能 > 内存/并发安全 > 停服 Dispose；禁止为 Editor 退出警告牺牲 Job。详见 [架构约束 §5.2](./联机机器人-架构约束.md#52-热路径优先级性能--安全--dispose)。

**PlayMode 交付门禁（摘要）**：改 Relay / 模拟真人操作 → EditMode `Regression` → EditMode `category=PlayMode` 单会话门禁全绿（覆盖 farm-wide 匹配独占与 Bot-vs-Bot 拒绝等当前行为）→ 再人工 Play。详见 [架构约束 §6.1](./联机机器人-架构约束.md#61-playmode-验收模拟真人操作交付门禁)。

**代码归属（一句话）**：本地 file package `cn.com.zerogame.unitypackages.terminator`（`ZGUPTerminator`）内的 `Terminator.MultiplayerBot*` 运行时、录制、Editor、测试与本文档集就是机器人权威实现，后续允许直接在包内维护；不要再把该包视为不可修改依赖。`BotConfig.asset` 继续留在使用方工程。其他 ZGUP 包的改动需单独评估，Server 撮合逻辑不为 Bot 特化。

**反射与录制 API**：Relay 热路径无反射，也不存在旧 Bot 协议分支。Editor 录制通过 Common 包公开的 opt-in completed-EndWrite journal（`BeginEndWriteCapture` / `SetEndWriteCaptureStamp` / `TryPeekCapturedEndWrite` / `ConsumeCapturedEndWrite` / `EndWriteCapture`）保留 payload、全局 sequence 与 producer `epoch + double timestamp`；不再扫描 transport pending slot。Replay 注入仍使用 `TryEnqueueSyntheticData`。

## 当前架构（一句话）

**Bot 与 ReplyServer 同进程共部署**（`Assets/Scenes/Server.unity` + `BotCoDeployBootstrap`）：单 Bot Listen Driver + `BotRelayManager` 虚拟端口；UTP 只用于原始 Connect 握手、当前真实 server hello、必要 link ACK 与 Server→Bot 下行，Connect 后全部 Bot→Server 业务 app 只经 Server inject API。应用层 `NetworkRelayMessageType.Connect(type=0)` 是当前远端成员重连状态，须按现行 app 结构精确解析，不能与 UTP 握手混为一谈。`Connected` 是唯一链路就绪事实源，只有收到本次真实 server hello 才置位。`session.matchID` 是唯一匹配绑定事实源，0 表示未匹配、非零值只由当前 `MatchToRead` 提交；已提交代次不可被另一非零 ID 覆盖，Server→Bot 的 Mismatch 通知只能取消相同当前代次；MatchToRead 到达即释放 outstanding matchingSlot。MatchStart 由 `LoginManager.__Start` 在 `Waiting` 边界单次发送，是 Bot 唯一进关授权，早到拒绝且不缓存；Play/ChapterStage 作为当前真人协议由 Bot 完整解析和消费，但不生成 Bot 进关状态。Invite 只接受当前完整协议布局与本次 Capture 的唯一 framing，不做旧 body、偏移或文本猜测；录像只接受 TRBT v2。Farm 内 `minBots`～`maxBots` 个 agent，**不是**多个 Headless 进程连 Server；`BotConfig.asset` 是使用方工程配置，不随包交付。
